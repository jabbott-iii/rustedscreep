# Architecture decision records

Format for each ADR: number, title, status (Proposed, Accepted, or Superseded by ADR-N), date, context, options, decision, consequences, evidence.
Claude proposes ADRs and the user accepts them. Numbers are never reused.

## ADR-001 Build toolchain: Accepted (2026-11-13)
- Context: SPEC §1 names wasm-pack (or cargo-screeps). cargo-screeps doesn't work with screeps-game-api ≥0.22, and the rustwasm org is archived (VERIFICATION_LOG S3, S8).
- Options:
  - (a) wasm-pack `build --target <verified>` followed by wasm-opt, which is what the starter uses.
  - (b) `cargo build --target wasm32-unknown-unknown`, then the wasm-bindgen CLI pinned to the crate version, then wasm-opt. This is more explicit and drops a tool dependency.
- Decide by: reproducibility, version-match enforcement, CI simplicity, and output parity with the loader.
- Evidence (VERIFICATION_LOG section F):
  - cargo-screeps 0.5.2 (2024-01-15) is the latest release, and the starter README says screeps-game-api 0.22+ is incompatible with it (V12). Option "cargo-screeps" is out (D1).
  - wasm-pack now lives at github.com/wasm-bindgen/wasm-pack, latest v0.15.1, 2026-10-30 (V6).
  - The starter runs `wasm-pack build --target web --release`, and wasm-pack runs wasm-opt `-O4` from Cargo.toml metadata. The starter does not pin the wasm-opt version (V15, V16).
  - The wasm-bindgen CLI must match the crate's schema version. Pinning the CLI to the exact Cargo.lock version is the safe rule (V4). wasm-bindgen 0.2.130 and wasm-bindgen-cli 0.2.130 are current.
  - binaryen version_133 has the lowering passes ADR-002 may need (V7, V8).
  - Both options produce the same `--target web` glue, which exposes `initSync({ module })` (V18).
- Recommendation: (b). The build script runs `cargo build --release --target wasm32-unknown-unknown -p rustedscreep-wasm`, then `wasm-bindgen --target web` at the exact Cargo.lock version (the script fails if the installed CLI differs), then a pinned binaryen `wasm-opt` with the ADR-002 flags. This pins every tool that touches the binary, and ADR-002 may need wasm-opt flags beyond what wasm-pack's metadata hook makes easy to audit. Cost: two tools to install (`cargo install wasm-bindgen-cli --version <lock>` and a binaryen release), and both installs ask first.
- Decision: (b), as recommended; the user accepted it on 2026-11-13 ("Accept all four", covering ADR-001, 003, 005 and 006 as recommended).
- Consequences: the P1 build script runs `cargo build --release --target wasm32-unknown-unknown -p rustedscreep-wasm`, then `wasm-bindgen --target web`, failing if the installed CLI differs from the Cargo.lock version, then a pinned binaryen `wasm-opt` with the ADR-002 flags. wasm-pack is not used. This is the deviation from SPEC §1 that D6 records. Installing the wasm32 target, wasm-bindgen-cli and binaryen needs the user's approval (rustup and cargo install always ask).

## ADR-002 Wasm feature target and Rust toolchain/edition: Accepted (2026-11-13)
- Context: Rust 1.82 and later emit reference-types and multivalue, and Rust 1.87 and later add bulk-memory (S6). The server's Node may reject these, and the starter documents `--signext-lowering` (S4).
- Options:
  - (a) Stable toolchain pinned to the newest version whose default features the probe accepts.
  - (b) Nightly with `-Ctarget-cpu=mvp` and `-Zbuild-std=panic_abort,std`, plus selected `+features`.
  - (c) Latest stable plus binaryen lowering passes, if they cover everything.
- Edition follows the toolchain (2024 needs a recent stable).
- Decide by: feature probe results (VERIFICATION_LOG §D), build reproducibility, and runtime CPU of the resulting wasm (measure).
- Constraint from the user (PROJECT_CONTEXT): stable only, pinned. Option (b) is therefore out.
- Evidence (VERIFICATION_LOG section F):
  - Rust stable is 1.100.0 (V13). Its wasm32-unknown-unknown default features are multivalue, mutable-globals, reference-types and sign-ext, plus bulk-memory and nontrapping-fptoint since 1.87 (V22). Turning them off for std needs nightly build-std (V23), which the user's policy rules out.
  - wasm-opt (binaryen version_133) can lower sign-ext, bulk-memory (memory.copy/fill) and nontrapping-fptoint. It has no multivalue or reference-types lowering pass (V8). A caveat: rustc's reference-types default may only change the call_indirect table-index encoding, so `--disable-reference-types` may still work on a real binary. Test this in P1.
  - The official servers have run Node 24 since 2026-04-01, per Screeps' own Steam announcement, which says the private server binaries were updated too (V62). It is an official changelog (priority 4), so the log marks it `inferred` until the probe confirms it per server. Node 24 supports all six Rust default features. By webassembly.org's table, Node added the last of them, reference-types, in 17.2 (V27). The starter dropped `--signext-lowering` and the mvp build on 2026-04-03 for that reason (V16). The probe confirms this on the MMO. The optional tracks probe the private server (PS1) and Seasonal (SE1).
  - The private server (screeps-launcher) installs Node 24 by default (V61).
  - Edition 2024 needs Rust 1.85+ (V25).
  - Local check: Node 18.19.1 (V8 10.2) already accepts all six default features (js/probe/check.mjs).
  - Probe on the official MMO, shard3, 2026-11-13 (V72): all six default features accepted, plus simd128, legacy EH, exnref and tail-call, with correct controls. The recommendation's condition is met on the core target, so no lowering pass or `--disable-*` flag is needed there.
- Recommendation: (a) with today's stable. Pin Rust 1.100.0 (or the stable current when P1 starts) in `rust-toolchain.toml`, use edition 2024, keep the default target features, and run wasm-opt `-O4` only, provided the probe accepts mutable-globals, sign-ext, nontrapping-fptoint, bulk-memory, reference-types and multivalue on the official MMO (core track). The optional tracks re-check it on the private server (PS1) and Seasonal (SE1). Fallbacks, in order: if a server rejects only sign-ext, bulk-memory or nontrapping-fptoint, add the matching wasm-opt lowering pass (c). If it rejects reference-types or multivalue, test `--disable-*` on a real binary. If that fails, pin the newest older stable whose defaults pass (edition 2021 below 1.85). On that path criterion (MSRV 1.86) and proptest (MSRV 1.88) need older versions (ADR-006).
- Decision: (a), as recommended; the user accepted it on 2026-11-13 ("Accept all three", covering ADR-002, 008 and 011 as recommended).
- Consequences: `rust-toolchain.toml` pins Rust 1.100.0 (the local machine has 1.99, so P1 installs 1.100.0 and the wasm32 target, and rustup asks first). Every crate uses edition 2024. The wasm build keeps the default target features, and wasm-opt runs `-O4` with no lowering pass. The private (PS1) and Seasonal (SE1) tracks re-run the probe and apply the fallback chain only if their server rejects a feature.

## ADR-003 Trap and abort recovery: Accepted (2026-11-13; (b) adopted only after P1 measurement)
- Context: SPEC §1 asks to re-instantiate on the next tick and never brick the bot. The starter uses `Game.cpu.halt()` after an aborted tick because of wasm-bindgen #3130 (S5).
- Options:
  - (a) `Game.cpu.halt()`. This is simple and proven, but costs a full global reset plus recompile.
  - (b) Discard the instance and the glue module (clear the require cache), then instantiate a fresh one from the cached `WebAssembly.Module`. This is cheaper if it is sound.
  - (c) A hybrid: try (b), and fall back to (a) after repeated failures.
- Decide by: P1 `trap-test` results (time to recover, CPU, correctness over 10 consecutive traps) and whether `halt` is available per server.
- Evidence (VERIFICATION_LOG section F):
  - The starter loader runs require, `new WebAssembly.Module` and `initSync` in one tick once the bucket gate (1500) passes. If `running` is still set at the start of a tick, it calls `Game.cpu.halt()`. Its catch block logs but does not reset `running`, so any thrown trap also leads to a halt on the next tick (V17).
  - `halt()` resets the runtime and wipes the heap. The isolate's heap limit is about 256 MB plus terrain data on the private server (driver 5.3.0, V43). The MMO limit is unverified, and the probe's env part reports `heap_size_limit`.
  - Unwinding on wasm needs nightly and build-std (V26), which the user's stable-only policy rules out, so panics abort and recovery has to live in JS (D3).
  - `Game.cpu.halt` exists on the official MMO (V72). The MMO heap limit is about 740 MiB (V73).
  - Open question for P1: whether the `--target web` glue can be initialized a second time. That means reading the generated glue for the pinned wasm-bindgen to see how `initSync` treats an already-set instance, and whether the glue must be re-evaluated as a separate module.
  - Answered in P1.4 (2026-11-14, V97): `initSync` cannot re-initialize, because it returns early once an instance exists. wasm-bindgen 0.2.130's `--experimental-reset-state-function` exports `__wbg_reset_state()`, which builds a new instance from the module the glue holds and reruns the start function. The build passes the flag, so (b) is available in every build.
  - P1.4 sandbox evidence (V99; node:vm following the open-source runtime, V96): 10 forced traps in a row recovered with (a) in 3 ticks each (11 globals) and with (b) in 2 ticks each (1 global, no halt). Both are correct there; the MMO trap-test still has to measure cost and correctness before (b) can become the default. The halting tick's Memory is discarded (V96), so the loader records each incident on the trap tick and halts on the next one.
- Recommendation: (c), the hybrid. Ship (a) as the P1 baseline because it is proven. Prototype (b) behind a config flag and adopt it only if `trap-test` shows it is correct over 10 consecutive traps and cheaper than a halt plus recompile. Back off after repeated failures.
- Decision: (c), the hybrid, as recommended; the user accepted it on 2026-11-13 ("Accept all four", covering ADR-001, 003, 005 and 006 as recommended).
- Consequences: the P1 loader ships the halt-based recovery (a) first. Re-instantiating from the cached Module (b) goes behind a config flag, off by default, and becomes the default only if `trap-test` shows it correct over 10 consecutive traps and cheaper than a halt plus recompile. The measured numbers and the final default are recorded here in P1. Backoff and one notification per incident apply in both modes.
- P1 measurement on the MMO (2026-11-14, V148): mode (a) recovered from 10 forced traps in a row, 3 ticks each (a new global per trap; only the last global logged its boot cost, 6.12 + 5.32 CPU over its two boot ticks, since each of the others trapped in its first loop, and the `booted in` cost line follows a first loop that finished, V149), and the bot ran on. Mode (b) was not run on the MMO: a live run needs a build with `recovery_mode` reinstantiate (a profile or stage option, not available yet). So (a) stays the default; switching to (b) needs its own 10-trap MMO run, which can also show the CPU it saves.
- Recovery bound (the P1 gate's "ADR-003 bound"; the user's decision at the P1 gate, 2026-11-14): in halt mode (a) the bot's loop runs again on the third tick after a trap (the halt tick, the new global's load-and-compile tick, then its instantiate-and-loop tick; `rustedscreep.trapTest` counts from the trap tick to the tick on which a fresh instance next runs, even when that run is the next scheduled trap), and it never bricks. Met by 10 traps in a row on the MMO (V148) and in the sandbox (V99). SPEC §1's next-tick re-instantiation (TypeScript glue, item 3) is mode (b) (VERIFICATION_LOG D2).

## ADR-004 Persistence encoding: Accepted (2026-11-14)
- Context: RawMemory segments are strings. Persist only data that must survive a reset, in a compact, versioned form, written only when dirty.
- Options: (a) base64 of a binary layout, (b) a denser UTF-16 packing scheme, (c) a hand-rolled varint layout with either of those.
- Decide by: bytes per segment, encode and decode CPU (bench plus in-game), and robustness against corruption (checksum).
- Evidence (VERIFICATION_LOG sections F and G):
  - RawMemory has 100 segments (ids 0-99), at most 10 active at once, and 100 KB per segment. Requested segments appear on the next tick, and the driver rejects oversize writes at end of tick (V41). Memory itself is capped at 2 MB (V40).
  - The segment and Memory limits are checks on JS string `.length`, so they count UTF-16 code units, not bytes (V40, V41, read verbatim in the driver).
  - Every segment present in `RawMemory.segments` at end of tick is re-saved and counts toward the 10-segment cap. Exceeding the cap throws after the loop and likely loses the tick (V41, inferred; V119), so the segment manager must unload segments it no longer needs.
  - Capacity per segment: base64 carries 76797 bytes in 102400 units (76781 of payload after the 16-byte header); a 15-bit packing carries 192000.
  - The string crossing decides the CPU, not the encoding's density (V123). The wasm-bindgen glue copies ASCII text into wasm in a JS loop and sends everything else through the TextEncoder/TextDecoder polyfill (the MMO has neither, V72), which converts a 15-bit unit to 3 UTF-8 bytes per code point in JS. Measured locally on one full segment (Node 18.19.1, a copy of the glue's loop and the repo's polyfill, the codec compiled to wasm; relative numbers only, the MMO runs a newer Node):

    | Path | Write (encode + CRC-32 + crossing) | Read (crossing + decode + CRC-32) |
    |---|---|---|
    | (a) base64, stock glue | 124 + 196 + 632 µs = 12.7 µs/KiB | 134 + 121 + 196 µs = 6.0 µs/KiB |
    | (b) 15-bit, stock glue | 617 + 429 + 1577 µs = 14.0 µs/KiB | 706 + 755 + 429 µs = 10.1 µs/KiB |
    | (b) 15-bit, inline-JS crossing (a build change) | 617 + 429 + 388 µs = 7.6 µs/KiB | 135 + 755 + 429 µs = 7.0 µs/KiB |

    CRC-32 costs about 2.3 to 2.6 µs/KiB in wasm (Adler-32 0.5, FNV-1a 1.0, both weaker on short records). At the volumes the bot will persist (a few KB per write), the difference between the paths is well under 0.01 CPU per write.
  - Storage fidelity: the driver stores the string as given (V121); the open-source storage path is JSON over UTF-8 (inferred lossless on Node 12 or later); the MMO's storage is closed source, so whether non-ASCII code units survive there is unverified (V121). A bulk UTF-16 crossing needs inline JS (V125).
  - In the sandbox the plain build's self-test (`node js/tools/persist-sim.mjs`, the bundle in a Node vm context with the polyfill) measured a full segment at about 0.33 to 0.6 ms to encode, 0.23 to 0.29 ms to read and 0.46 to 0.7 ms to decode and compare. The JS write took 8 to 13 ms on the first large crossing of a global (the polyfill's decoder is not optimized yet) and 0.8 to 1.9 ms on later runs; the cold read took 2.4 to 3.1 ms (2026-11-14).
- Recommendation: (a) with CRC-32. Through the stock glue it is cheaper than (b) per payload byte in both directions, its ASCII text survives any storage, and it needs no custom JS. (b) is faster only with an inline-JS crossing, which needs a build change, and it is safe only after a live round trip proves the MMO keeps every code unit; neither is worth it at the expected volumes. A tag in the frame names the encoding, so (b) can be added later without breaking stored data.
- Decision: (a) base64 with CRC-32, as recommended. The user chose "base64 + CRC-32 (Recommended)" on 2026-11-14 (P1.9).
- Consequences:
  - Frame (container format 1, `rustedscreep_core::persist::frame`): `"rs1b"` (magic `rs`, version `1`, encoding `b`), then base64 (RFC 4648 section 4 alphabet, no padding, strict decoding) of a 16-byte little-endian header (owner kind u16, schema u16, write tick u32, payload length u32, CRC-32/ISO-HDLC u32 over the first 12 header bytes and the payload) followed by the payload. Every decode failure (empty, foreign, unknown version or encoding, bad base64, short, length or CRC mismatch, another owner's kind or schema) is an error the owner answers by rebuilding from game state.
  - The CRC is the one the loader and tools already use (js/src/crc32.ts, js/tools/lib/crc32.mjs), so a JS tool can check a frame.
  - Payload layouts belong to their owners and are versioned by `schema`; option (c), a shared varint writer, waits for the first owner that needs one.
  - The 15-bit option stays open: a new encoding letter, the inline-JS crossing, and a live round trip of every code unit on the MMO first.
  - The live round trip on the MMO (the P1 gate) is `rustedscreep.persistTest()` (TEST_PLAN §8). It passed on shard3 on 2026-11-14: a full segment (76781 bytes in 102400 units) written and read back intact, at 0.79 CPU to encode, 5.77 to write (cold), 0.31 to read and 1.14 to decode (V144).

## ADR-005 Constants source for native tests: Accepted (2026-11-13)
- Context: pure crates must test natively, and constants should come from the API (SPEC §0).
- Options:
  - (a) `rustedscreep-consts` re-exports `screeps-game-api` constants and local types, which requires the crate to build and run natively.
  - (b) `rustedscreep-consts` mirrors the values with sources, and the in-game self-check catches drift.
- Decide by: R4 (native build of screeps-game-api).
- Evidence (VERIFICATION_LOG section F):
  - screeps-game-api's own CI runs `cargo clippy --all-features` and `cargo test --all-features` on native Ubuntu. lib.rs has no `target_arch = "wasm32"` gate. The only cfg gate is `feature = "mmo"` (V29).
  - In `constants`, five files are free of JS bindings. find.rs, look.rs, small_enums.rs and types.rs use `#[wasm_bindgen]` (look.rs has a crate-private extern block), but their public items are plain Rust values and enums that compile natively. `local::RoomName`, `Position` and `LocalCostMatrix` are pure logic, apart from conversions from JS types and Position's JS-wrapping `game_methods` (V30). wasm-bindgen is a plain dependency and compiles natively. Calling a JS-backed function natively would fail at runtime (inferred).
  - The crate already exports most CPU and memory limits (`INTENT_CPU_COST`, `CPU_BUCKET_MAX`, `CPU_TICK_LIMIT_MAX`, `PIXEL_CPU_COST`, `MEMORY_SIZE_LIMIT`, `MEMORY_SEGMENT_SIZE_LIMIT`, `MEMORY_SEGMENT_ACTIVE_LIMIT`, `INTER_SHARD_MEMORY_SIZE_LIMIT`; V34-V42), so `extra.rs` needs fewer hand-written values.
  - The purity hook already blocks `screeps::` in rustedscreep-core and JS-backed screeps modules in rustedscreep-consts.
- Recommendation: (a). rustedscreep-consts re-exports `screeps::constants` and the pure `screeps::local` types, and a native `cargo test -p rustedscreep-consts` smoke test (for example `RoomName` parsing plus a constant) proves it in P1. Values the API does not export go in `extra.rs` with their sources. (b) stays the fallback if a future crate version stops building natively.
- Decision: (a), as recommended; the user accepted it on 2026-11-13 ("Accept all four", covering ADR-001, 003, 005 and 006 as recommended).
- Consequences: rustedscreep-consts depends on screeps-game-api and re-exports `screeps::constants` and the pure `screeps::local` types. A native `cargo test -p rustedscreep-consts` smoke test in P1 proves the native build. `extra.rs` holds only values the crate does not export, with sources and dates. Native code never calls JS-backed functions, and the purity hook enforces the module boundary. If a future crate version stops building natively, this ADR is superseded by (b).

## ADR-007 Base planner approach: Accepted (2026-11-18)
- Context: SPEC §3.3 asks for an automatic base planner (stamp/bunker or distance transform) with incremental, cached placement. ROADMAP P4 decides between the candidates by benchmark on a terrain corpus.
- Options: (a) stamp or bunker layouts, (b) distance transform with flood fill and min-cut ramparts, (c) a hybrid.
- Decide by: corpus validity, rampart count, path lengths, planner CPU (criterion), and time-sliced in-game cost.
- Candidates (P4.2, `rustedscreep-core` planner/, both resumable one phase per `Run::step` for the Optional tier). They share one referee (`planner::validate`: counts per level from `CONTROLLER_STRUCTURES`, the site rules, reach from the first spawn level by level, the spawn rule of V174, lab ranges, the economy's roles by position, rampart and wall repair reach, and the defense rule of V247 at every level from the first rampart level), the economy's tiles (`planner::sites`: mining tiles, containers, links, extractor), the roads (`planner::roads`), the hub's anchor score (`planner::score`) and the minimum cut (`planner::mincut`, `planner::defence`), so they differ in layout and rampart policy only.
  - (a) `planner::bunker`: an 11 × 11 core stamp (cut down to radius 5, 4, 3 or 1 where it does not fit), a 4 × 4 lab stamp and extension pods in 8 orientations, singles for the rest, and a rampart over every protected structure from that structure's level.
  - (b) `planner::flood`: a hub core where the distance transform allows, a flood fill outward along a diamond road lattice, a lab stamp, and the minimum-cut ramparts (`defence::levels`: the line from the first rampart level).
  - (c) The hybrid: (a)'s layout with (b)'s minimum-cut ramparts (the harness's `with_min_cut`, applied in one call; adopting it means writing a ramparts phase for (a)).
- Evidence (2026-11-18, the planner after three review rounds; the 72-room corpus of P4.1: one sector of shard3, E1–E9 × N51–N59, every room with a controller, 39 with two sources and 33 with one (V233); three modes: fresh, a standing spawn on open ground, and one within `CONTROLLER_CLEAR` of the controller (70 rooms); `cargo test --release` of tests/planner_bunker.rs and tests/planner_flood.rs (`measures`, the ignored `step_costs`) and tests/planner_cases.rs (`-- --nocapture`); means over the plans unless stated; paths, tower damage and inside area on the RCL8 plan):
  - Validity: every plan of (a), (b) and (c) is valid in every mode, 214 of 214 each, with defense checked at every level from RCL2. (a) and (b) are deterministic and give the same plan stepped one phase at a time with a new scratch each step; (c) has no run of its own. The hand-made rooms of tests/planner_cases.rs pass for both. Seeded fuzz of synthetic rooms on this code (the review's, kept in the session scratchpad, not in the repo; four seeds of 1500 generated and 16 hand-made rooms, 42,346 inputs per candidate with up to six standing spawns each): no panic, hang, stepped-versus-whole mismatch or exposure at any level; no plan invalid through a planner fault (one per candidate is tagged so by the fuzz's own classifier but has no valid plan on inspection: a standing spawn closing the room's only exit corridor). (a) found no plan for 771 inputs (1.8%) and (b) for 747; of those 702 each were `NoRoom("mining tile")` and 8 `NoRoom("mineral container")` on inputs that allow none. The rest: (a) labs 50 (the hand-made pillar and pit rooms, where its 4 × 4 lab stamp does not fit), controller link 10, core 1; (b) core 24 (pillars: no open 3 × 3), controller link 10, labs 2, mining tile 1. 129 plans per candidate were invalid as given (122 sources whose only tiles touch an earlier source, so the economy reads their containers wrong; 7 standing spawns that trap creeps whatever the plan).

  |---|---|---|---|
  | Ramparts at RCL8 (most in a room, fresh) | 86 / 86 / 86 (86) | 27.0 / 28.3 / 27.9 (73) | 26.3 / 25.9 / 27.0 (74) |

## ADR-008 Loader language and transpile target: Accepted (2026-11-13)
- Context: SPEC asks for a TypeScript loader. The starter says Babel is required for the older Node on official servers (S3).

- Evidence (VERIFICATION_LOG section F):
  - The official servers run Node 24 since 2026-04-01 (V62, an official announcement, `inferred` until the probe confirms it), and the starter now sets Babel preset-env `targets: { node: 24 }` (V21). The probe measures the real JS syntax level on each server (21 syntax checks, ES2015 to ES2022).

## ADR-013 When Critical work stops: Accepted (2026-11-14)
- Context: SPEC §3 and CLAUDE.md say Critical (spawning, defense, harvesting) "always runs". The scheduler (ROADMAP P1 module 6) also has to keep the tick below the engine's kill. The kill is a wall-clock timeout at tickLimit + 5 ms, at least 30 ms (VERIFICATION_LOG V105), while the clock the scheduler can read, `Game.cpu.getUsed()`, is isolate CPU time plus 0.2 per intent (V106). Running past tickLimit costs in two ways. A killed tick is an aborted tick, which the loader recovers from with a global reset and a recompile (ADR-003). And while the bucket is below 500 − limit, tickLimit is bucket + limit, so a tick that runs past it without being killed is billed into a negative bucket and the next tick is skipped (V37). There is also an unverified user report of negative `getUsed` readings on the MMO (V106).
- Options:
  - (a) Critical never stops: it runs every unit every tick, whatever the clock says.
  - (b) Critical stops only at the ceiling (tickLimit minus `tick_reserve_pct`), which it shares with the other tiers, and it runs first, so the others get only what it leaves. With a clock that has given `bad_samples_to_break` (2) bad readings in a tick, every tier stops, Critical included, for the rest of that tick.
  - (c) Like (b), but on a broken clock Critical goes on with an estimated clock: the last good reading plus the units run times a conservative cost per unit.
- Decision: (b), as recommended; the user accepted it ("Accept ADR-013", 2026-11-14). P1.6 implements it. Critical runs first and takes what it needs up to the ceiling, which is 90% of tickLimit; at 450 of 500 CPU that is far more than a colony's Critical work needs. It stops only where continuing risks a reset or a skipped tick, which would cost more Critical work (the whole aborted tick and its recovery) than the units it skips. (a) cannot guard against either outcome. (c) keeps Critical running on a clock that has stopped working, with an estimate that is only as good as the last measured cost per unit, so it can still overrun. It is the option to revisit if live runs show bad readings are real and frequent. The other tiers' bucket gates never apply to Critical.
- Consequences: on a tick that reaches the ceiling, Critical jobs that run after it are skipped for that tick. Round-robin cursors start the next tick with the units that were skipped. `rustedscreep.scheduler()` shows budget stops and a broken clock, and TickStats counts tier-order breaches. `bad_samples_to_break` is a config field (TUNING.md), so the threshold can be raised without a code change.
- Evidence: V37, V105 and V106 (driver cf63d8a, engine a90d26f; researcher and skeptic). The P1.6 tests pin the behavior: `the_ceiling_keeps_the_reserve`, `an_empty_bucket_still_runs_critical`, `bad_clock_readings`, `the_break_threshold_is_configurable`, `a_cost_jump_stays_inside_the_reserve`.

## ADR-015 Wasm delivery through the GitHub link: a base64 text module: Accepted (2026-11-14; amends ADR-012; `deploy/`'s wasm form amended by ADR-028)
- Context: the first live deploy through the link (ADR-012) showed that the sync uploads every file of the linked folder as a text module named after the file: `main.js` became `main`, and `rustedscreep_wasm.wasm` became a text module `rustedscreep_wasm.wasm`. The loader's `require('rustedscreep_wasm')` failed with "Unknown module", and requiring the `.wasm` name makes the engine evaluate the wasm bytes as JavaScript (V136, V137; engine game.js:551-594). No binary file can reach the account intact through the link, and the user keeps the link: "I am leaving it linked because what we make will be live tested with the link" (ADR-012).
- Options:
  - (a) Keep the link and ship the wasm as base64 text in a JavaScript module, `deploy/rustedscreep_wasm.js` = `module.exports = "<base64>";`, which the sync turns into module `rustedscreep_wasm`; the loader decodes the string to bytes before its CRC-32 check and compile.
  - (b) ADR-012's fallback: unlink the integration and upload a `{binary}` module through the API (`npm run deploy -- --server mmo`, which needs Node 22 or 24 and is not written yet).
- Evidence (local, 2026-11-14; the design research, re-measured in the repo's sandbox):
  - Decoding 230513 bytes with a plain-JS decoder (`atob`, `Buffer` and `TextDecoder` absent, as assumed for the MMO, V95, V139): 5.4 to 6.3 ms cold on Node 18.19.1, 1.8 ms on Node 26.13.1. Evaluating the 307373-byte text module: 1.1 to 1.3 ms. End to end in the boot's load step (load + CRC), the smoke sandbox measured 3.1 ms with a binary module and 8.0 ms with the text module on Node 18 (the research: +6.1 ms on Node 18, +3.0 ms on Node 26). The cost is paid once per global boot (the engine caches a module per global); compile, instantiate and the tick are unchanged, because the decoded bytes are the same wasm (its CRC-32 and sha256 equal the build's).
  - Upload budget (V76): the text-module upload is 13 characters longer than the binary one, since a binary module is stored as base64 too (375913 against 375900 of 2097152 characters at this build). Heap: about 0.36 MB more for the global's lifetime (the module source and the string, kept by the module cache).
  - Alternatives measured and rejected: the base64 inside main.js (+0.8 ms to compile main.js on every global, even when the boot is deferred); a separate decode tick (one idle tick more per global reset, to save 3 to 6 ms of bucket); `atob` when present (never probed on the MMO); other encodings (hex twice the size; base85 or UTF-16 schemes add decoder complexity or Unicode hazards through the sync).
- Decision: (a). The user chose "option 1" on 2026-11-14, after asking whether it keeps the benefits of Rust: it does, since only the transport changes; the decoded bytes are the build's wasm, and the loader compares their CRC-32 with the build's (on a mismatch it logs `MISMATCH` and notifies once, then boots anyway, as before ADR-015; refusing to boot on a mismatch would be a separate loader decision).
- Consequences:
  - `deploy/` holds `main.js` and `rustedscreep_wasm.js` (the `.wasm` as one ASCII line of padded standard base64). (ADR-028: when one module would pass 905709 bytes, the largest the link has delivered intact, the base64 is split across `rustedscreep_wasm.js`, `rustedscreep_wasm_1.js`, ….) `npm run stage` builds into its own `target/stage-dist`, checks both files' sha256 against the build and that the text module decodes to the build's `.wasm` before writing anything, copies them and checks the copies, then removes a `rustedscreep_wasm.wasm` an earlier stage left and checks that the folder holds only the staged files. It reports the sha256 and CRC-32 of the decoded bytes; the boot log compares the CRC-32.
  - The loader's `toBytes` accepts a binary module's view or ArrayBuffer (an API upload, a private server, the sandbox) or a base64 string, decoded by `js/src/base64.ts` (strict: a bad length, character or padding is a load incident, never compiled). The CRC-32 check runs over the decoded bytes. The boot line shows the form that ran (`wasm String(base64, N chars)`) and now also reports `typeof atob` and `Buffer` (V139).
  - The build writes `dist/rustedscreep_wasm.js` and runs the smoke test with both forms; the sandbox evaluates the text module in the driver's module wrapper, once per global (V138). `npm run size` counts both upload shapes and checks the larger. The bundle check bans `atob`, `btoa` and `Buffer` in main.js (V95's safe default).
  - The decode runs in the boot's existing load step. If a live `load+crc` figure ever crowds that tick, a separate decode phase can be added then, from the measurement.
  - If the link ever delivers binary files, the loader still accepts them; `deploy/` must then hold only one of the two forms, since both map to one module name.
  - The ADR-012 fallback (b) stays documented; the deploy tool, when written, uploads the binary form.
  - The loader's backoff record (`Memory.rustedscreepLoader`) carries a failed deploy's incident streak into the next build, which then waits up to `backoffMaxTicks` (3200) before booting and keeps the streak after it boots. After a push that follows a failed build, once `rustedscreep.status()` shows the new build ID, run `delete Memory.rustedscreepLoader` in the console (run earlier, the old build rebuilds the streak). Resetting the streak when the build ID changes would remove this step; it changes the persisted record and the backoff across pushes, so it is the user's decision.
  - The `rustedscreep_wasm.wasm` text module the first sync left on the account is not removed by the bot. Whether a later sync deletes it is unverified (V77); otherwise the user deletes it once in the in-game Script editor, since it counts toward the 2 MB code limit. (Settled since: a sync deletes every module missing from `deploy/`, V145; the user had already deleted this one by hand.)
  - Each staged build commits a 307 KB text file (base64 deltas poorly in git), about 0.3 MB of repository growth per changed wasm.

## ADR-018 The `Memory.creeps` entries `spawnCreep` leaves behind: Accepted (2026-11-15)
- Context: every successful `StructureSpawn.spawnCreep` reads the `Memory` global and sets `Memory.creeps[name]` to `options.memory`, the entry already there, or `{}` (engine structures.js L1124-1130, V181). The bot keeps no creep state in `Memory` (CLAUDE.md: keep the tick path off `Memory`; identity is the name, P2.3), so nothing reads these entries and nothing removes them. Each one adds about 20 UTF-16 units (`"wE4N59-9wt7g1v":{},`) to `Memory`, whose limit is `MEMORY_SIZE_LIMIT`, 2 MB of UTF-16 units (V40), for good. The read on a spawn tick already costs that tick a `JSON.parse` of `Memory` and the stringify at the end (V33), whichever option is chosen, and both grow with `Memory`. The minimal spawn path (P2.3) ships with option (a) so this decision stays open.
- Options:
  - (a) Leave the entries. No code. `Memory` grows by about 20 units per spawned creep: a room spawning 10 creeps per `CREEP_LIFE_TIME` adds about 0.13 units per tick, and the 2 MB limit is about 15 million room-ticks away (for example 1.5 million ticks with 10 such rooms), with each spawn tick's parse and stringify slowly growing.
  - (b) Remove the entry in the same act step, right after the call returns OK: `delete Memory.creeps[name]` through `Reflect` with `catch`, about 4 JS calls per spawn. No extra parse (the call already made the engine read `Memory` that tick). `Memory.creeps` stays `{}`. Our code then touches `Memory` on spawn ticks, only to undo the engine's own write: the invariant becomes "the tick path never reads `Memory`, and writes it only to undo `spawnCreep`'s entry".
  - (c) Set `Memory.creeps` once to a value that is not an object, so the engine writes no entry (`_.isObject` is false; it replaces only `undefined`, L1124-1126). One write ever and no per-spawn cost. But `creep.memory` in the console would no longer work, and the engine's other uses of `Memory.creeps` (the `Creep.memory` accessors in creeps.js) were not read, so whether any of them throws on a non-object is unknown (VERIFY before choosing).
  - (d) Clean up dead creeps' entries periodically: a `Memory` read on each cleanup tick (its own parse) plus the list of live names; the most code, for no gain over (b).
- Recommendation: (b). It keeps `Memory` at its current size with no extra parse and no unread engine path, at about 4 JS calls per spawned creep (a few per thousand ticks per room). (a) is acceptable for P2's single room: about 2700 units over the gate's 20000 ticks at 10 creeps per `CREEP_LIFE_TIME`.
- Decision: (b), the user's decision on 2026-11-15 ("accept ADR-018 option b").
- Consequences:
  - After each `spawnCreep` that returns OK, rustedscreep-wasm spawn.rs deletes `Memory.creeps[name]` for that name only (`Reflect.deleteProperty` with `catch`; nothing when `Memory` or `Memory.creeps` is not an object). The parse already happened in the call, and the driver stringifies the parsed `Memory` at the end of the tick (V180), so the entry never reaches the stored string. Cost: 8 JS calls per accepted order (two key strings, two `Reflect.get`, two object checks, the name string and the delete).
  - The architecture invariant becomes: the tick path never reads `Memory` for state, and writes it only to undo `spawnCreep`'s entry (this ADR) or to reset a `Memory` that does not parse (ADR-019). CLAUDE.md and `.claude/rules/wasm-bot.md` say so.
  - Entries other code wrote (another script's creeps, a creep spawned from the console) are left alone.
- Evidence: V33, V40, V181 (engine structures.js L1121-1217 at a90d26f, read byte-exact; supersedes V172), V180 (the driver's end-of-tick save). The sandbox test checks the entries are gone from the stored string (js/tools/spawn-sim.mjs). Not measured live: the parse and stringify cost of a spawn tick.

## ADR-019 Spawning while `Memory` is unusable: Accepted (2026-11-15)
- Context: a successful `spawnCreep` reads `Memory.creeps` (V181). When the raw `Memory` string does not parse (or is JSON null), the engine's `Memory` getter gives null for the tick (game.js L479-499), and every `spawnCreep` that passes its checks throws a TypeError before recording anything (structures.js L1124, V181). Null is the only `Memory` that does this: a primitive makes the engine's write a silent no-op (V181). The bot never writes `Memory` (the loader keeps its record there only on incidents), so the raw string turns invalid only through something else (a `RawMemory.set` by hand, another script). Until it is repaired, nothing spawns, and nothing in the bot repairs it: the colony dies out over `CREEP_LIFE_TIME` ticks without human action. The loader reports an unusable `Memory` only on the first loop after a boot (main.ts, V96, V99). P2.3 logs each throw with the JS error's message and counts it as a fault; a throw holds the spawn for `spawn.hold_ticks`.
- Options:
  - (a) Log only (P2.3 as shipped). Recovery needs a human.
  - (b) Repair: when a spawn order throws and `Memory` reads null, set the raw `Memory` to `{}` (`RawMemory.set`), notify once (`Game.notify`), and let the next tick spawn. Whatever the raw string held is lost, but it was already unreadable to every script, and the loader's record is rebuilt (its backoff state resets). Our code writes `Memory` only in this failure.
  - (c) Repair at boot only: the loader, which already detects an unusable `Memory` on its first loop, resets it there. A corruption during a global stays until the next reset.
- Recommendation: (b). It keeps the colony recoverable without a human, which CLAUDE.md asks of the loader for traps, at the cost of a raw string no script could read. Not decided here, because it writes and discards the user's `Memory`.
- Decision: (b), the user's decision on 2026-11-15 ("accept ADR-019 option b").
- Consequences:
  - When a `spawnCreep` call throws, spawn.rs reads the `Memory` global (cached for the tick after the call's own read); if it is null, it calls `RawMemory.set("{}")` (with `catch`), logs a warning, sends one `Game.notify` per global, and releases the spawn's hold so it tries again on the next tick. The driver's end-of-tick save then keeps `{}`, because it stringifies the parsed `Memory` only when that is truthy (V180). The tick's remaining spawn orders are not called (each would throw the same way); their jobs ask again next tick.
  - Only a null `Memory` triggers it, the one case that makes `spawnCreep` throw (V181). A raw string that parses to a non-object (which the loader also calls unusable) is left alone: spawning works with it.
  - What the raw string held is lost. The loader, which keeps its record in the heap and does not halt while `Memory` is unusable (V96), moves that record back into `Memory` on its first read once `Memory` is an object again, so this global's incident and backoff history carries on and halt recovery (ADR-003 mode a) works again (js/src/main.ts `loaderMemory`; js/tools/trap-sim.mjs `repair`). Without a heap record (the loader did not read `Memory` while it was null), the record rebuilds from defaults on its next read.
- Evidence: V96, V99, V181 (engine game.js L479-499 and structures.js L1122-1130 at a90d26f, read byte-exact; supersedes V172's line numbers), V180 (driver runtime.js `RawMemory.set` and the end-of-tick save at cf63d8a). The sandbox test corrupts the raw string and checks the throw, the reset, the one notification and the next tick's spawn (js/tools/spawn-sim.mjs).

## ADR-020 Construction sites before the P4 base planner: Accepted (2026-11-15)
- Context: the RCL1–3 opening (P2.4) builds every own construction site its room has and fills every spawn and extension, but nothing in the bot places a site: placement of extensions, towers, roads and the rest is P4's base planner (ROADMAP P4, ADR-007 decided there). A fresh room therefore runs RCL1–3 on its spawn's 300 energy (`SPAWN_ENERGY_CAPACITY`) unless someone places sites by hand, which the P2 gate rules out ("reaches RCL3 with no manual action"). RCL2 allows 5 extensions and RCL3 10 (`CONTROLLER_STRUCTURES`), each `EXTENSION_ENERGY_CAPACITY[level]` (50 at RCL1–7) and `CONSTRUCTION_COST` 3000 to build. Bigger bodies need the capacity: at 300 a worker is one repeat of [WORK, CARRY, MOVE]; at 550 two, at 800 four, so the same income moves in fewer creeps and fewer intents. P3's static miners (5 WORK for a source's 10 energy per tick) cannot spawn at 300 at all. `Room.createConstructionSite` is verified in part (V200): its game-side checks and the RCL count, but not its billing, whether sites placed earlier in the same tick count toward the limit, or the rule for tiles next to exits.
- Measured (native scenario, `economy::tests`, 2026-11-15; an open room with walls on its border, two sources 13 and 18 tiles from the controller with 8 open tiles each, `OPENING_MMO`): a fresh room (RCL1, a full spawn, no creeps) reaches RCL3 in 8022 ticks with no extension (`a_fresh_room_reaches_rcl3_without_extensions`), and in 5892 ticks when the level's extension sites are placed at each level-up and the workers build them (`a_fresh_room_reaches_rcl3_building_its_extensions`): 2130 ticks, 27%, sooner, after spending 15000 energy on the extensions. The source-limited floor is 2260 ticks (`CONTROLLER_LEVELS[1] + [2]` at two sources' yield).
- Options:
  - (a) No placement until P4. The opening builds only sites placed by hand. RCL1–3 (and P3) run at 300 capacity; nothing P4 might want to move gets built early. The P2 gate's RCL3 run takes longer (8022 ticks in the scenario).
  - (b) Interim placement of extensions only, from RCL2: a small deterministic pattern near the first spawn (for example a checkerboard on free tiles at range 2 to 4, away from the sources' and the controller's open tiles and from exits), placed in the Optional tier as the level allows, one `createConstructionSite` per tick, with a rescan of the room after each (`Movement::invalidate`). P4 adopts what is built or replaces it: dismantling a misplaced extension later loses at most its 3000 energy (at most 30000 for RCL3's ten). Needs the unverified parts of V200 checked first (billing, same-tick counting, exit tiles), or kept safe by placing one site per tick and only on tiles at least 2 from any edge.
  - (c) Bring P4's extension stamp forward now: placement that P4 keeps, but it needs P4's layout decision (ADR-007) first, which wants the terrain corpus and both candidate planners benchmarked.
- Recommendation: (b). It is real performance at RCL2–3 (27% sooner to RCL3 in the scenario, and P3 needs the capacity), at a bounded cost if P4 lays the base out differently, and it is a small module (a pattern, a job and one binding). Not decided here: it places structures before the planner that owns placement exists, which is the user's call.
- Decision: (b), the user's decision on 2026-11-15 ("accept ADR-020 option b").
- Consequences:
  - A pure pattern in rustedscreep-core (`economy::placement`): extensions on the tiles of the first spawn's checkerboard parity at range 2 or more from it, nearest by path first, never on a wall, a road, a structure or a site, next to a source or a mineral, within 3 of the controller, or within 3 of the room's edge (which keeps clear of the exit rules V200 leaves open). The other parity stays free, so every tile the pattern leaves stays connected to the spawn by diagonal steps, and every extension has a free neighbor to be filled from.
  - A new Optional job in rustedscreep-wasm (planning is Optional, CLAUDE.md): per owned room with a spawn, while its extensions and extension sites are fewer than `CONTROLLER_STRUCTURES[extension][level]`, it picks one tile and the act step calls `Room.createConstructionSite(x, y, "extension")` (bound with `catch`); at most one call per room per tick, so a site never races another one's count (V200). A refused tile is skipped for the rest of the global. `opening.place_extensions` turns it off at runtime (for example before P4 takes over).
  - P4's planner keeps or replaces the extensions it finds; replacing one loses at most its 3000 energy.
- Evidence: V200, V203 (billed 0.2 CPU per accepted call), V204 (no same-tick counting on the game side; the processor drops the excess), V205 (the edge and exit rules); the scenario tests above, and with the bot's own placement `a_fresh_room_reaches_rcl3_with_no_manual_action`: RCL3 in 6029 ticks (2026-11-15), against 8022 without extensions and 5892 with sites placed by hand on another row; ROADMAP P2 and P4.

## ADR-027 Persist each room's plan anchor and adopted role tiles: Accepted (2026-11-18)
- Context: the base plan is held in the heap only and rebuilt from what stands after a global reset (ADR-007, ADR-026). Two windows give a different plan than the one the room was built from, and with `planner.replace` on its structures in the new plan's way are then destroyed one at a time: (1) the anchor spawn destroyed and a reset before its site is placed; (2) an adopted container or link that predates the plan lost and a reset before it is re-sited (ADR-026's residual risks, with the review's measurements). Separately, a room at RCL7 or later runs every anchor at each reset (up to 3 flood runs and validations, Optional and sliced) when it holds anything off its plan, or when a later spawn sorts above its first one (61 of the corpus's 284 room-levels).
- Options:
  - (a) Keep the plan heap-only and accept both windows (a few ticks each, after an attack or a loss).
  - (b) Persist per owned room its anchor tile and the tiles of the adopted containers and links (a few bytes a room) in a RawMemory segment of the persistence layer (ADR-004's versioned, checksummed format, written only when they change). On a rebuild the persisted anchor is tried first, even with nothing standing on it, with the persisted role tiles fed back as standing, and its plan is kept without trying the others when it validates and its spawn tiles hold every standing spawn (a change to `planner::job`'s anchor rule, which today stops early only on a plan holding everything that stands); a missing or corrupt record, or a plan that fails those checks, falls back to today's rule.
  - (c) Persist the whole layout (about 216 items at RCL8, about 650 bytes a room): no rebuild at all, at the cost of a larger record and a migration whenever the planner's output changes.
- Recommendation: (b). It closes both windows and, with its rule change, makes the anchor search one run, with a small record that a planner change does not invalidate.
- Decision: (b), the user's choice on 2026-11-18 ("Accept option (b)").
- Consequences of (b): a new segment or record version and its round-trip, corrupt-data and size tests in `js/tools/persist-sim.mjs`; `planner::job::Facts` gains the persisted anchor and tiles, and the anchor rule keeps the persisted anchor's plan when it validates and holds every standing spawn (a native test: a reset with off-plan structures runs one anchor); the planners' own rules are unchanged.
- Evidence: the P4.3 fix-round review (2026-11-18): the anchor-loss probe (72 of 72 rooms flip without the site, 72 of 72 recover with it), the adoption probe (707 of 3907), and the anchor search's cost (E7N57 at RCL8: 26.9 ms native for one run, 81.7 ms for three).
- Implementation (2026-11-18): `planner::record` (schema 1: per room the packed room name, the anchor tile and up to `max_adopted()` adopted containers and links, 5 + 3 bytes each; a malformed payload refuses the whole record), owner kind 3 (`persist::kind::PLANNER`) in segment `PersistConfig::planner_segment` (96). `planner::job`: no room is planned before the record's load has finished; `Facts::with_record` adds the entry's anchor and adopted tiles; a run tries the record's anchor first and keeps its plan once it validates and holds every standing spawn; an entry is set when a plan is ready and dropped when its room is no longer owned. rustedscreep-wasm `persist.rs` loads and writes it as the config record is; `rustedscreep.planner()` shows the record and an anchor "from the record". A refused record is written again at once; a segment whose text never arrived (`LoadError::Unavailable`) is left as it is and that global writes nothing, so a good record is not lost to a read failure; entries of rooms no longer owned are dropped also while `planner.enabled` is off. Evidence: `planner::record` and `planner::job` unit tests (each new rule mutation-checked); `js/tools/planner-sim.mjs` over three globals (the record written, a reset planned from it in one run with no destroy, a corrupted record refused with one warning and written again). Deviation from the consequences above: the record's round trip and corrupt-record checks are in `planner-sim.mjs` and its size bound in `planner::record`'s tests, not in `persist-sim.mjs`, which only counts the second segment loaded at boot.

## ADR-028 Wasm modules over the GitHub link's size limit: Accepted (2026-11-18; amends ADR-015, and ADR-012's `deploy/` contents)
- Context: build `614db580737b-421df93f` (P4.3's placement and ADR-027's record) staged a 1306109-byte `rustedscreep_wasm.js`, the first module above 1 MB. After the push (commit 5217308) `require('rustedscreep_wasm')` returned a plain Object on every load while the 88775-byte `main.js` beside it ran, and the bot ran no code, Critical work included, for about 320 ticks (84352809 to 84353131) until the user pushed a rollback to `f3e7dbd63bfe-cee9042d` (STATUS 2026-11-18). What has arrived intact: modules up to 905709 bytes, and pushes up to 993365 bytes in all (that build's two files); the failed push was 1394884 bytes (V257). For a file between 1 MB and 100 MB, GitHub's contents API supports only the raw and object media types, and the object type returns an empty `content` (V256; the default type's behavior is not documented); an empty module's `module.exports` is `{}`, which fits. The open-source backend's code upload keeps module names as given (escaping `.`, `/` and `\`, dropping a name that starts with `$`) and rejects a whole upload only over its 5 MiB total (V258, V32). Not verified: that the MMO's sync uses that endpoint, whether its limit is per file or per push, and whether 1 MB means 1,000,000 or 1,048,576 bytes (V257, V259). Every build of the current tree is larger than the module that failed: plain wasm 979566 B, trap-test 979684 B, profiler 1014021 B, act-test 987113 B (sandbox only), each 1.31 to 1.35 MB as base64. So, under V257's inferred cause, no build of the current tree can reach the MMO, and P4.3 and ADR-027 are off it. Neither `/check` nor `npm run stage` checks a module's size, only V76's total.
- Options:
  - (a) Split the base64 text across several text modules, each file at most 905709 bytes, the largest seen intact (V257; raised only after a larger module arrives intact). `deploy/` holds `main.js`, `rustedscreep_wasm.js` (part 0) and, as needed, `rustedscreep_wasm_1.js`, `rustedscreep_wasm_2.js`, …, each `module.exports = "<base64>";` on one line. The text is cut at multiples of 4 characters, so each part is canonical base64 on its own and only the last may end in `=`, into `ceil(characters / 905688)` parts of equal length within 4 characters (905688 characters plus the 21-byte wrapper is 905709 bytes): today's 1306088 characters become two parts of 653044 (files of 653065 bytes), the profiler build's 1352028 two of 676012 and 676016, and two parts serve up to 1811376 characters (1358532 bytes of wasm). A module of at most 905709 bytes stays one, the same files as today. The build records each part's length in main.js's `BUILD` (`wasmParts`, for example `[653044, 653044]`). The loader requires each part on a boot attempt, refuses a part that is not a string of its recorded length (a load incident before any decode), decodes each into its offset of one `Uint8Array` (no joined string), then runs the CRC-32 check as today. A binary module under `rustedscreep_wasm` (an API upload, a private server, the sandbox) is still used alone. It relies on the limit being per file, not per push: its first push would be about 1.39 MB, more than any push seen intact. The failed push's `main.js` arrived and ran, which a cap on the whole push would have to explain by delivering some files and emptying others, so per file is the likelier reading (inferred, V259).
  - (b) Compress the wasm with raw deflate before base64, in one module: 356838 bytes at level 9, 36.4% (475784 characters; brotli at quality 11 and window 24 gives 277135 bytes, 28.3%), measured with Node's zlib on this build's wasm. Its push would be about 564580 bytes, inside every size seen intact (module and push), and one module keeps today's name, so it relies on nothing (a) does. The loader needs an inflater in main.js: either the bundle rule (`.claude/rules/js-loader.md`: nothing bundled at runtime besides the wasm-bindgen glue) changes and package.json gains its first runtime dependency (an exact pin, under ADR-006's dependency review), or a hand-written inflate is added to `js/src` and tested like `base64.ts`. Its boot cost is unmeasured: it decodes 64% fewer base64 characters and evaluates a module 64% smaller, against the inflate itself. One module at 905709 bytes holds about 1.86 MB of wasm at this ratio (679266 deflated bytes; inferred).
  - (c) (b) with (a)'s split: compress, then split the text when one module no longer fits. It keeps (b)'s headroom past 1.86 MB, and the 2 MiB total would then hold about 4.1 MB of wasm at this ratio (inferred). (a)'s split code is reused as it is.
  - (d) Shrink the wasm so one module fits: under 679266 bytes for a 905709-byte module (a 30.7% cut from 979566), or under 749982 bytes if the cutoff is 1,000,000 (23%), and more for the profiler build. Size-first compiler settings (`opt-level` "s" or "z") would deviate from SPEC §1's release profile (`opt-level=3`), which needs a discrepancy row in VERIFICATION_LOG section C and the user's decision, and they usually trade tick CPU for bytes (not measured on this bot; the Criterion benches and a profiler window would show it), against the goal of the lowest CPU per tick (CLAUDE.md, SPEC). Finding the bloat is open-ended (the planner added about 300 KB: 260 KB with P4.3's placement, 40 KB with ADR-027's record), and later phases add code.
  - (e) ADR-012's fallback: unlink the integration and upload a `{binary}` module through the API. ADR-021 dropped the API tools, and the user keeps the link (ADR-012).
- Recommendation: (a), with the optional probe below first. It is the smallest change that restores deploys and keeps the loader's bundle rule; it changes only the transport (the decoded bytes are checked by the same CRC-32, which logs and notifies a mismatch but still boots, ADR-015); its parts stay at or under the largest module seen intact, so it does not depend on where the cutoff is, only on the limit being per file; and its split is the half of (c) that compression would later reuse. (b) is the choice if the probe, or a failed first split push, shows a cap on the whole push, and (b) or (c) is the next decision as the total budget nears (below), with the inflate's boot CPU measured first.
- Optional probe before the first split push (the user's step; Claude writes `deploy/` only when the user names `mmo`): push the live f3e7dbd files plus a dummy `rustedscreep_wasm_1.js` of about 650 KB (about 1.64 MB in all, above the largest push seen intact). The running build never requires it. If the module arrives intact (the in-game Script editor shows it; `require('rustedscreep_wasm_1').length` in the console, if the console can call `require`, V259), a digit-suffixed name syncs and the limit is not a 1 MB cap on the push. ## ADR-029 Remote mining before P8's scouting: room intel, creep identity, roads, and where the energy goes: Accepted (2026-11-22)
- Context: P6.2 (reservers, haulers, and roads) runs remote rooms, which are rooms the bot mines without owning them. Four things it needs are not in place yet.
  - **Vision.** The bot sees a room's sources and controller only while it has a creep or an owned structure there, or observes the room (V101: a reservation alone gives no vision). A room's terrain needs no vision (V156). Scouting and observers belong to P8.
  - **Identity across resets.** Every push to `main` is a global reset (V145), and a reset loses the heap. The bot keeps no creep state in `Memory`, so a creep's name is the only identity that survives (P2.3). Today a name holds the role, the home room, and a serial (`spawning::CreepName`). It does not hold a remote room.
  - **Builders.** P6.1's model (`economy::remote`) assumes that haulers on a road way carry one WORK part and repair the road as they walk. It charges the road and container builds as energy spread over `remote.horizon_ticks`, but it prices no builder bodies.
  - **Unload.** The live home (E7N57, RCL5 with capacity 1800 and one spawn) has no storage: `planner.storage` is off (the user's choice, 2026-11-18). Its haulers fill the spawns and extensions, then the controller container. The upgraders are sized to the energy that reaches them there (P3.4).
- Decision point 1: how the bot learns about candidate rooms.
  - (a) A minimal scout now. A scout role with one MOVE part (50 energy, 3 ticks of spawn time, a 1500-tick life) is ordered only while a home wants another remote and has a candidate it knows nothing about. Candidates are the rooms through the home's exits (`Game.map.describeExits`), leaving out highway rooms and sector centers (V231, inferred). The scout visits them nearest first. What it sees (sources, controller, owner, reservation, hostiles, and keeper lairs) is kept in the heap with the tick it was seen. A mined room stays visible through its own creeps, so after a reset only rooms not yet mined need another scout. P8's scouting replaces or extends this.
  - (b) Remote rooms named in the console, as `rustedscreep.remote(home, room)`, and kept in the config record. Nothing explores, and the first creep sent there gives vision.
  - (c) No look ahead: the first creep sent to each candidate is a reserver (650 energy), sent without knowing what it will find.
- Decision point 2: how a remote creep knows its room after a reset.
  - (a) The remote room in the name. New role codes for the scout, the reserver, the remote miner, and the remote hauler (never reused) put the remote room after the home: `<code><home><remote>-<serial>`, at most 31 bytes (the engine's limit is 100, V171). Old names parse as before, so this is an additive format change. The manager's active remote rooms are the ones its creeps name. Nothing new is persisted.
  - (b) A segment record. Each home's remote rooms and their intel go in a RawMemory segment (ADR-004's versioned, checksummed format, as ADR-027 did for the planner). Names stay as they are, and the creeps' rooms are rebuilt from the record.
  - (c) Heap only. Creeps are matched to rooms by where they stand. A creep still walking at a reset idles until the room is seen again.
- Decision point 3: who builds the roads.
  - (a) The haulers. Once `best_plan` chooses roads, the bot places road sites along each source's way outside the home room, one site a tick and under `MAX_CONSTRUCTION_SITES`. The haulers carry one WORK part, as the model prices them. A loaded hauler walking home builds any site within range 3, and every hauler repairs the road as it walks. The first build is slow: `BUILD_POWER` is 5 hits a tick per hauler, and a road site needs 300 hits on plain or 1500 on swamp.
  - (b) A remote builder role, a worker-like creep spawned while a remote room has sites.
  - (c) No roads in P6.2. `best_plan` picks only plans without roads, and roads come later.
  - In every option the remote miner builds its own container: it harvests into its one CARRY part and builds the site under it.
- Decision point 4: where the remote energy goes.
  - (a) Where the home's haulers take it: the spawns and extensions first, then the controller container. The upgraders' budget counts the remote yield, so they are sized to spend it. `planner.storage` stays off.
  - (b) Into storage. `planner.storage` is on by default (a storage costs 30000 energy to build). The remote haulers unload into it, and the home's fill and the upgraders draw from it. This is a larger change, because nothing reads storage today.
- Recommendation: 1(a), 2(a), 3(a), and 4(a).
  - 1(a) costs 50 energy per look. It needs no help from the user, and the scout is the smallest part of P8's scouting.
  - 2(a) keeps every remote creep's room in the one identity that already survives a reset, with no new segment to version.
  - 3(a) builds what the model prices and adds no role that sits idle once the roads stand.
  - 4(a) reuses the haulers' sinks and the upgraders' sizing and needs no storage before P9.
- Decision: 1(a), 2(a), 3(a), and 4(a), the user's choices on 2026-11-22 ("Minimal scout", "Room in the name", "Haulers build", and "Home sinks").
- Consequences:
  - `spawning::Role` gains four roles, and `Identity` gains an optional remote room, parsed only for those roles.
  - New pure modules in rustedscreep-core: the remote manager (candidates, intel, ways, the choice by `best_plan` under a spawn-time cap) and the remote creeps' tasks. The snapshot reads sources, containers, sites, piles, and the controller's reservation in the remote rooms it mines.
  - The upgrading budget takes the remote yield as an input.
  - P8 extends the scout.
- Evidence: V101, V145, V156, V171, V200 (sites in a neutral or own-reserved room), V231, V263, and V264; P6.1's model figures (STATUS 2026-11-22).
- Implementation (2026-11-22, P6.2): as decided, in rustedscreep-core `economy::Remotes` and rustedscreep-wasm `remote.rs`, with three choices the decision left open.
  - **Tiers.** The `remote` job, which picks the rooms and makes the requests, is Critical like every job that requests creeps (the scheduler runs Critical jobs before Standard ones), but it requests and searches only on ticks the Standard tier runs, so remote mining stays spare work.
  - **Scouts' rooms.** The snapshot also reads the room an own scout stands in, so a scout's tour of the home's other candidates gives intel without each room being named in its creep's name.
  - **Roads.** Roads are read only every `remote.road_read_ticks`, in a room a remote hauler stands in, and road sites go out only on those ticks.

  After a global reset, a room with creeps is searched again from the `remote` job, and its creeps hold with a request meanwhile, so movement keeps reading the room. Evidence: `economy/remotes_tests.rs`; `js/tools/remote-sim.mjs` (row 23 of `npm run check`); V267 and V268.

## ADR-030 A controller signer: one cheap creep that signs every controller it can reach, tougher only for towered rooms: Accepted (2026-11-22)
- Context: the user asked (2026-11-22) for a creep that signs controllers with the text "jabbott.dev rustedscreep bot - https://github.com/jabbott-iii/rustedscreep" (74 characters, under the 100 that common's `userString` keeps, V276). The rules:
  - It is the cheapest body that reaches a controller and signs it.
  - It goes to every controller it can physically reach, whoever owns the room.
  - It is sent to a controller only once a way there is known.
  - At most one exists at a time, and none is spawned once every reachable controller carries the text.
  - In a hostile room it carries enough TOUGH parts to survive until it has signed.
  - Neither `docs/SPEC.md` nor the roadmap has a signer. P8's scouting (`docs/ROADMAP.md`, "Scouting and observers") is the nearest item, so this record adds one.
- The game's rules it rests on:
  - `signController` needs range 1. The engine checks only that the creep is not spawning, the target is a controller, and the range. It checks no ownership, reservation, or safe mode, so any controller can be signed (V274, V275). Another player's safe mode blocks attacks and heals, not moves or signs (V280).
  - A controller with the server's sign (`hardSign`, set for a planned novice or respawn area) shows that sign under the username `Screeps` (`SYSTEM_USERNAME`), and a player's sign stays hidden while it lasts (V275). Such a room counts as unsignable until a recheck.
  - A sign is a billed intent, 0.2 CPU (`INTENT_CPU_COST`, V276).
  - One MOVE part costs 50 energy, and a creep made only of MOVE parts never gains fatigue, so it walks one tile a tick on any terrain for its 1500-tick life (V54, V170).
  - Tower damage is summed and applied in each creep's own tick, after every intent. So a creep signs on the tick it takes lethal damage (V278). Unboosted TOUGH parts are plain hit points (V279). A tower needs `TOWER_ENERGY_COST` (10) energy per shot, and the owner's towers fire during their own safe mode (V281). Damage by range is V239.
  - A room whose `Game.map.getRoomStatus` differs from the home's is walled off or closed (V168).
- Decision point 1: how far it goes.
  - (a) One creep life: every room that can have a controller and that a route from a home spawn reaches within `CREEP_LIFE_TIME`.
  - (b) A radius of `sign.max_distance` rooms.
- Decision point 2: what the bot remembers across global resets (a reset discards the heap).
  - (a) A compact record per room in a new RawMemory segment, written only when it changes. Rooms already signed are rechecked after `sign.recheck_ticks`.
  - (b) The heap only. After a reset the tour starts again from the rooms nearest home.
- Decision point 3: the CPU tier.
  - (a) Optional. Requests and moves run only while the Optional tier runs, and the spawn priority is below every other role.
  - (b) Standard.
- Recommendation: 1(a), because it matches "any controller it can physically reach". 2(a), because a reset would otherwise send a creep back to rooms it already signed. 3(a), because the sign is cosmetic and must never take CPU or spawn time from the economy.
- Decision: 1(a), 2(a), and 3(a), the user's choices on 2026-11-22 ("One creep life", "Persist and recheck", "Optional tier").
- Design (within the user's rules; each threshold is a `sign.*` config field):
  - **Rooms.** The candidates are the rooms a room name says can have a controller (not highways or sector centers, the rule `economy::is_remote_room` already uses, V231) within `sign.max_distance` rooms of a home. The default, 31, is `CREEP_LIFE_TIME / (ROOM_SIZE - 1) + 1`: a straight walk crosses at most that many rooms in one life. The route's length is the real bound.
  - **The way first.** A room is due when the record holds nothing on it, when it was seen without the text, or when a recheck or retry comes due. Before a signer is given a due room, the bot searches a route there with PathFinder (`sign.route_max_ops`, `sign.route_max_rooms`). The search fails at once for a room whose status differs from the start's (V168). The route must be found and fit the signer's remaining life less `sign.life_margin_ticks`. The search avoids rooms whose towers the bot has seen and rooms that killed `sign.max_deaths` signers, except the target, and the route it found is the one the creep walks (searched again from the new signer's first tile). Only the search from a home spawn makes a room unreachable, until `sign.retry_ticks` have passed. A search that fails from where the live signer stands only passes the room over for that signer.
  - **Look, then sign.** A room no creep has seen is first a look: the signer walks two tiles in, and vision gives the controller's tile, its sign, its owner, and the owner's towers. Then it signs, after a route to a tile next to the controller is found. A controller walled off from every entrance is unreachable.
  - **The body.** A target whose way crosses no seen tower gets the plain signer, one MOVE part. A towered target gets the cheapest body of TOUGH parts in front and MOVE parts behind, at most `MAX_CREEP_SIZE` parts and within the home's energy capacity, that survives the worst case. In the worst case every seen tower hits it on every tick from the target room's entrance until the tick it signs, each at its range's damage (V239), plus `sign.damage_margin_pct`.
    - The walk is modeled a tick at a time in the engine's order: the move, then the fatigue the MOVE parts left take off, then the tick's damage (V55, V278). The step's terrain sets the fatigue (V54, V154), and unknown roads count as their terrain.
    - Damage takes the front parts first (V283): the TOUGH parts, then the MOVE parts one by one. A dead MOVE part stops taking off fatigue, and a dead TOUGH part still weighs (V284). So a body that has lost MOVE parts walks slower and stays longer under the towers.
    - The body survives when it reaches the tile next to the controller with hits above 0 and a MOVE part for every step before it. Each TOUGH part is 100 hit points for 10 energy (V282), against 50 for a MOVE part, so TOUGH parts make a surviving body cheaper.
    - A room no body survives is deadly until `sign.retry_ticks` have passed. A creep in a towered room takes at least 150 damage a tick, so even a body of 50 parts lives there about 34 ticks: only short walks under fire can be signed.
  - **Safety.** A plain signer that walks into a room and sees towers there stands on the entrance edge, so the engine carries it back out (V151), and the room is planned for a tougher signer. A signer that dies before its life ends counts a death in the room it was in. After `sign.max_deaths` deaths, or after `sign.max_overwrites` times that another player replaced the text after it was signed (or a sign did not show on the next read), the room waits `sign.retry_ticks`. Defending creeps are not modeled. A signer that has walked a towered room takes only targets with no modeled damage afterward, since its hit points are not read.
  - **One at a time.** One signer for the whole bot, requested by the home nearest the next due room, at `PRIORITY_SIGNER` (70, below the scout's 75). A signer with nothing left it can reach ends its life (`suicide`), and none is spawned while nothing is due.
  - **When it starts.** A home sends signers from `sign.min_level` (3, the level remote mining starts at), so the RCL1 and RCL2 opening keeps every 50 energy. The record's segment is requested only then, and only once the config overrides have loaded, so an override that turns the signer off holds from a global's start. Nothing goes into the book before the record loads.
  - **The record.** Owner `persist::kind::SIGN` in segment `persist.sign_segment` (95). Per room it holds the state, the tick last seen, the controller's tile, the seen towers' tiles, and the death and overwrite counts. It is written when a room's entry changes, at most once per `sign.save_ticks`.
- Consequences:
  - `spawning::Role` gains `Signer` (code `g`, never reused). Its name is `g<home>-<serial>`, so old names parse as before.
  - The snapshot reads the room a signer stands in: the controller as an object, its `sign` (`username` and `text`), and the hostile towers' tiles.
  - The act layer gains `signController(target, text)`.
  - Movement gains a public route search that keeps the route it finds, with rooms to avoid, and a room-status lookup through the installed router.
  - CPU: while it walks, about one move intent (0.2 CPU) a tick plus movement's share; a route search per target (heavy units, Optional); one sign intent per room. No cost while nothing is due.
- Risks:
  - Players whose controllers carry the text see it, and some answer visitors. An owner whose code re-signs its own controller is capped by `sign.max_overwrites`.
  - Defending creeps can kill a signer the tower model calls safe, which `sign.max_deaths` caps.
  - While the bucket is below the Optional threshold, the signer does not run; one left on an edge tile then crosses back and forth each tick (V151). The tier rule was kept over a Standard-tier exception for that case.
  - A route search that runs out of ops before reaching a room marks it unreachable until a retry.
  - The step back out does not save a one-part signer from towers that fire on the tick they see it: one shot deals at least 150 damage (V239) against its 100 hit points, and damage lands after the move (V278). The first live run lost one 50-energy signer this way in E6N57, a room the bot had not seen before (V285). The bot learns of towers only by seeing them, so each such room can cost one creep once; its towers are then recorded and the room is planned with them, or marked deadly.
- Evidence: V274 to V284 (2026-11-22, three screeps-verifier researchers against engine a90d26f and screeps-game-api 0.23.5); V285 (the first live run, 2026-11-22).

## ADR-032 Rampart upkeep and home road repair: when the line is built, how high it is held, and who repairs: Accepted (2026-11-23)
- Context: ROADMAP P7 lists rampart upkeep. ADR-007 left two questions to P7: when the ramparts are built, and the level policy. ADR-026 has the phase that uses a kind turn its planner switch on (`planner.ramparts`, off until now).
  - A new rampart has `RAMPART_HITS` (1) and is gone at its first decay step, about `RAMPART_DECAY_TIME` (100) ticks after it is built, unless repaired (V302, V304). A rampart loses `RAMPART_DECAY_AMOUNT` (300) every 100 ticks after that. So placing ramparts without a repairer wastes their sites.
  - E7N57's flood plan stands 37 ramparts from RCL2 (a native probe of the plan on the room's terrain with its live spawn, 2026-11-23). Of these, 36 are on the edge line along the room's west and north sides, about 40 tiles from the towers at (43, 19) and (43, 23). The room is at RCL5.
  - The same session found that home roads were never repaired. P3.5 left road repair for "a periodic structure scan with P4", and P4.3 placed roads without one. The user saw roads decaying ("workers are no longer trying to repair roads and containers"). The containers were repaired as P3.5 designed: a worker walks to one only below `repair.walk_pct` (50%). So a container between 50% and 80% waits for a worker that happens to be within 3 tiles. A road lasts about 50000 ticks unworn (V242), and the base planner placed E7N57's roads from about Game.time 84384350. The user chose to fold road repair into P7.3, since ramparts need the same periodic read of hits.
  - Repair energy: a creep's repair gives 100 hits an energy (`REPAIR_POWER` a WORK part for `REPAIR_COST` a hit, V222). A tower's repair gives 20 to 80 hits per 10-energy shot (`TOWER_POWER_REPAIR` with falloff, V296). Its line in E7N57 is at the falloff floor (20).
- Options (when ramparts are built, and how high they are held):
  - (a) Turn placement on now and hold every rampart low: `upkeep.rampart_permille` (10, so 1%) of `rampart_hits_max` at the level. That is 100000 hits at RCL5, 3000000 at RCL8. Raising E7N57's 37 ramparts costs about 37000 energy once, paced by the room's workers, and decay costs about 1.1 energy a tick.
  - (b) Build the upkeep but leave placement off, for a later item to turn on.
  - (c) Turn placement on and keep ramparts only alive, at a small floor, until a later item raises them.
- Options (who repairs):
  - (d) The opening's workers do every repair: containers (P3.5), roads, and ramparts.
  - (e) Towers also repair roads and containers within 5 tiles when no threat is open and they hold a reserve.
- Decision: (a) and (d), the user's choices on 2026-11-23: "Line now, held low" and "Workers only". Towers keep every shot for fights. P7.2 already noted that they can run dry under fire.
- What it does (P7.3):
  - `planner.ramparts` is on. The plan's ramparts (and walls, none in E7N57's plan) are sited from their level, `planner.max_sites` at a time.
  - Reads (`rustedscreep-wasm` snapshot): every `upkeep.read_ticks` (50) ticks, each owned room's roads come through the engine's road filter (about 7 calls a road) and each own rampart's `hits` is read (1 call). Between those reads, a rampart is read when first seen, and only the road or rampart a repairing worker stands within one step of reach of is read. The road is read by id, with one `Game.getObjectById` (V308). The workers ask for these reads in the Standard work, so a tick whose Standard tier does not run asks for none. A road whose last read leaves at most one repair of the room's worker body also asks for the other roads under repair within that reach, so a worker that finishes one road finds the next already read.
  - Memory (`economy::Opening`, heap only): each room's roads by tile, and its ramparts' last hits by handle. A road asked for and not read is gone. A global reset forgets both. The next read refills the roads, and each rampart is read again when first seen.
  - Repairs: a road below `upkeep.road_start_pct` (50%) of its `hitsMax` is repaired to full. A rampart below `upkeep.rampart_start_pct` (90%) of its target is raised to the target. In both cases one worker takes each repair, lowest share of its goal first, and the nearest worker takes it. These wait for a room with no site to build. A road below `upkeep.road_urgent_pct` (20%), a road a worker repaired on the tick before (so it is finished first, a few ticks), and a rampart below `upkeep.rampart_floor` (3000 hits, or its target if lower) go before the sites, as the containers always have. So a new rampart is repaired by the builder that finished it, before the next site. A rampart's raise above the floor still gives way to a new site, since raising one takes many loads.
  - Off (`upkeep.enabled`), nothing is read or repaired, and the rooms forget their roads and ramparts.
- Consequences:
  - The opening's `Task::Repair` now carries a `Fix`: a container, a road by tile, or a rampart by handle. `rustedscreep.opening()` gains `roads N (to repair M, lowest P%)` and `ramparts N (target T, below it B, lowest hits H)`.
  - Seven `upkeep.*` config fields (TUNING.md).
  - `repair.walk_pct` stays at 50. P3.5's measurement (TUNING.md) found that walking to every container below 80% lost 1.43 to 1.55 upgrade progress per energy repaired, against 0.83 to 1.02 at 50. A container at 50% still has about 12500 ticks of decay left. With workers now walking to roads and ramparts, a worker passing within 3 tiles of a container below 80% repairs it on the way, as before.
- Risks:
  - Every owned room's full read lands on the same tick (Game.time divisible by `upkeep.read_ticks`), which is also a remote road-read tick. With one room that is about 270 JS calls every 50 ticks. P8's expansion should stagger the read by room (the hot-path review, 2026-11-23).
  - Constructed walls placed by the ramparts' gate are not repaired: they have no owner, so the snapshot does not list them, and they stay at `WALL_HITS` (1). E7N57's plan has none.
  - During a threat, ramparts' hits are read only every `upkeep.read_ticks`, apart from the one being repaired. Siege repair is P7.5's (defenders) or a later item's.
  - The rampart raise costs energy that would otherwise go to upgrading. The share is a config value. P9's surplus may raise it.
  - Workers walk about 40 tiles to E7N57's edge line, on the room's exits. Nothing keeps a worker away from the line while hostiles are in the room. The towers and P7.5's defenders answer threats there.
  - Road wear (V54) is not modeled in the native scenarios. A heavily used road decays faster than modeled, but `upkeep.road_urgent_pct` still puts it before the sites.
- Evidence: the native probe of E7N57's plan (37 ramparts, 33 roads at RCL5); V236, V241, V242, V302 to V308; the native scenario tests in `economy/tests.rs` (Upkeep, P7.3).
- Amendment 1 (2026-11-23, after P7.3 went live as `137131369c69-dirty-83e81a71`): the workers are sized for the repairs, and a rampart started below the floor is refilled. Accepted with the user's choices "Yes, fix it here" and "Add a refill band".
  - Context: the first live reads showed E7N57's 2 workers at 1 WORK, 1 CARRY, 1 MOVE. While upgraders take the controller's energy (P3.4), the worker solver (P3.6, `economy::sizing::worker_value`) kept exactly `opening.min_workers` and counted only builds, the mining containers' repairs, and fills as their work. Road and rampart decay was not counted, so neither the count nor the body grew for the line. From the constants: 37 ramparts lose 37 × 300 hits every 99 ticks, about 112 hits a tick (V304), while one such worker 40 tiles from the line repairs at most about 38 hits a tick.
  - The native world model (`economy/tests.rs`) then showed a second problem. With every rampart of a line below `upkeep.rampart_floor`, a worker took each rampart just back over the floor (a few hundred hits) and walked to the room's lowest one, often 10 to 20 tiles along the line. Two 2 WORK, 3 CARRY, 2 MOVE workers spent 26% of their time repairing, and a 40-rampart line about 38 tiles from the controller lost about 16 hits a tick net.
  - Decision, sizing: `WorkerTargets` gains `repair` (what the room's roads and own ramparts lose to decay over one creep life, `sizing::road_decay` and `sizing::rampart_decay`, in energy) and `repair_trip` (the way from the controller to them, each weighted by what it loses). The solver counts their repair rounds as work, and the room keeps at least the whole workers that its sources' fractions and all its repairs (containers, roads, ramparts) take together, within `opening.min_workers` to `opening.max_workers`. The plan is built again when the count of known roads or ramparts changes. For E7N57's numbers (37 ramparts and 38 roads about 40 plain tiles out, 2300 energy) the solver gives 2 workers of 2 WORK, 3 CARRY, 2 MOVE, whose repair rounds take 1.67 of their 2.00 workers' time; at 30 tiles, 3 of 1 WORK, 2 CARRY, 1 MOVE.
  - Decision, refill band: a rampart a worker has started below the floor stays before the room's sites until `upkeep.rampart_refill` (6000 hits, twice the floor; at least the floor). Each rampart carries its repair state (`Mend`: none, raised toward the target, or refilled). In the world model at RCL5 with upgraders (2 workers of 2 WORK, 3 CARRY, 2 MOVE), 40 ramparts set at the floor at once along the far edge went over two creep lives from 120000 total hits to 135700 with the band, with 8 of them lost and the lowest left at 2200; without it, to 67600, with none lost yet and the lowest at 500.
  - Consequences: one more config field (`upkeep.rampart_refill`, `FIELD_COUNT` 140) and one cross-field rule (floor at most refill). No change to the snapshot, the act step, or any persisted format.
  - Risks, measured in the world model:
    - The repair rounds are lower bounds (the walk's fatigue rounding, and no walk between targets along the line), so the count can still fall short. In the same world, with the 40 ramparts built from sites 10 at a time, the repairs of the first 20 kept both workers busy, and since urgent repairs go before sites, the third batch of sites waited for more than a creep life.
    - With many ramparts at the floor at once the band loses some (8 of 40 above) while it lifts the line as a whole. Live, the planner places sites `planner.max_sites` (10) at a time.
    - A long rampart line stays expensive whatever the rule. The user's next request, mixing constructed walls into the line (walls do not decay), is the planned answer.
    - The upgraders' budget does not subtract the workers' repair energy (about 1.2 energy a tick for E7N57's line), so the upgraders are sized slightly larger than the energy left for them.

## ADR-033 Walls in the rampart line: gates, the walls' target, and the ramparts walls replace: Accepted (2026-11-23)
- Context: the user asked to "mix walls with the ramparts to create choke points and lower the maintenance burden", and then that the policy "automatically applies to all potential rooms and new starts without having to recode it".
  - ADR-007's plan closes the line with ramparts only (the minimum cut, with walls only where a rampart cannot stand; E7N57's plan had none). A rampart loses `RAMPART_DECAY_AMOUNT` (300) every `RAMPART_DECAY_TIME` − 1 ticks whatever its hits (V304), so a long line costs its workers all their time (ADR-032's amendment: a 40-rampart line about 38 tiles out kept two 2 WORK workers busy and still slid below the floor).
  - A built constructed wall never decays (V309). It has 1 hit when built and `WALL_HITS_MAX` (300000000) as `hitsMax` from RCL2 (V310), costs 1 energy to build, with 2500 allowed per level apart from the ramparts (V311), and is repaired and broken exactly as a rampart of the same hits is (V314, V316). It blocks every creep, the owner's too, while the owner's own rampart lets them pass (V313). It has no owner, so it is not in `Game.structures` (V315).
- Options asked (2026-11-23, with the walls' facts above):
  - Gates (the line's tiles that stay ramparts): (a) where the plan's roads cross the line, plus one for each outside region the base must still reach, on the cut tile nearest the towers; (b) as (a), plus a rampart every 10 tiles along long walls.
  - The walls' target: (c) the ramparts' (`upkeep.rampart_permille` of the level's `rampart_hits_max`, with the same floor and refill); (d) a separate share.
  - The standing ramparts on tiles that become walls: (e) a wall site under each (V312) and the rampart left to decay; (f) destroyed now (ADR-026's replacement).
- Decision: (a), (c) and (e), the user's choices: "Roads + one per exit region", "Same as the ramparts", "Wall under them, let decay". Then, after the hot-path review noted that upkeep held every constructed wall in a room, the user's "I want upkeep limited to the plans walls": only walls on the plan's wall tiles are held.
- What it does:
  - Planner (`planner::defence`, the plan's rampart step, for every plan the bot makes): `gates` keeps as ramparts each cut tile under a planned road and each that may not take a wall (a tile the plan keeps clear, or one with another planned structure). Then it joins every region of the ground hostile creeps reach from the exits to the base: reach is grown from the hub (or a standing spawn's neighbors) over the ground as the plan will stand, and each region own creeps cannot reach yet gets the cut tile between it and reached ground that is nearest a planned tower (then the hub, then index), until no region can be joined. `apply` places walls on every other cut tile, at the line's level. A gate that opens only on an inside pocket (ground the cut keeps from hostile creeps only to keep them out of ranged reach of a structure, V243) does not count for its region: E6N58's first version of the rule walled its region off that way, which the corpus test caught.
  - Placement (`planner::build`): a wall's site may go under an own rampart (V312). An obstacle of unknown type on a planned wall's tile is the wall built (only movement's scan sees a wall, V315). A wall counts as reached when reached ground lies within `REPAIR_REACH`, as the validator already judged walls (the walls of a line stand next to each other).
  - Snapshot (`rustedscreep-wasm`): each owned room's constructed walls on the full upkeep read, through the engine's filter (`{structureType: "constructedWall"}`, one `find` and the same per-object reads as a road), and by id between full reads when a repairer asks (`ObjectKind::Wall`).
  - Upkeep (`economy::Opening`): walls are held as ramparts are (`Fix::Wall`, by tile: below the floor before the sites up to the refill, then raised to the target in a room with no site), and only the plan's: the placement hands each room's planned wall tiles to the opening as it looks at the plan (`Opening::set_plan_walls`), so a previous owner's wall, one built by hand, or a novice area's border wall is left alone, and a room whose plan is not ready yet (after a global reset) holds none until it is (walls do not decay). A wall reading 0 hits or 0 `hitsMax` is skipped too (V317). A rampart whose tile holds a wall, or an own wall site since the last full read, is not repaired, so it decays away. Walls add nothing to the workers' repair sizing (they do not decay). `CreepIntent::RepairObject` now also targets walls. `rustedscreep.opening()` gains `walls N (target T, below it B, lowest hits H)`.
  - Every room: the policy lives in the plan's rampart step and the upkeep rules, which run for each owned room, including a fresh start and each room P8's expansion claims. Nothing names a room, and nothing is persisted for it (ADR-027's record holds only the plan's anchor and role tiles). The one switch is the existing global `planner.ramparts`, which places ramparts and walls together.
- Consequences:
  - E7N57's plan: 5 ramparts (gates at (2, 6), (27, 3) and (46, 35), a road gate at (4, 43), and one over a structure at (44, 26)) and 32 walls, where it had 37 ramparts. Its line's decay drops from about 1700 to about 230 energy a creep life (`sizing::rampart_decay`, 46 energy a rampart). Raising the 32 walls is a one-time cost of up to their target each, paced by the workers like the ramparts' raise.
  - The corpus (214 plans: every corpus room, planned fresh, with a standing spawn on open ground, and with one by the controller): 1011 ramparts (338 of them gates off roads, the rest on roads or over structures) and 4635 walls, where all 5646 were ramparts. Every plan stays valid: the validator's exits rule (every side whose exits the bare room reaches still has one), its reach rules, and its defense rule, which counts walls as part of the line.
  - E7N57's live transition: its standing rampart sites are built as ramparts, then a wall site goes under each, and those ramparts decay away unrepaired.
- Risks:
  - A gate is a rampart, so hostile creeps break in through gates or walls alike (both are held at the same target). The choke point helps the bot more than it slows an attacker: gates near the towers put own creeps' way out under the towers' fire.
  - A tile the plan keeps clear stays a gate, so some rooms keep more gates than regions (338 gates off roads over 214 plans).
  - Placement counts any obstacle of unknown type on a wall's tile as the wall. A previous owner's structure there would count too, though upkeep repairs only constructed walls on the plan's tiles.
  - The full upkeep read gains one `find` and about 4 to 7 calls a wall (E7N57: about 200 calls every 50 ticks for its 32 walls). Not measured live yet.
  - The test harness's ADR-007 comparison (`with_min_cut`) still measures an all-rampart line for the bunker candidate. It is test tooling only.
  - ADR-032's risk that constructed walls are not repaired is resolved here.
- Evidence: V309 to V316 (screeps-verifier, engine a90d26f, common 2fb779b, crate 0.23.5); the native tests listed in TEST_PLAN.md §1 (Walls, ADR-033); the corpus test `every_line_is_walls_but_its_gates` in `tests/planner_flood.rs`.

- Context: the user asked for "a makefile like the one from Nadir for creating new releases through tag push", and a CD (continuous delivery) workflow that publishes:
  - the Rust crates to crates.io;
  - "release files that are just the files in the deploy folder";
  - a Steam Workshop release "that contains those same files".

  - What the release ships:

  - How the Workshop job reaches SteamCMD:

    - (d) a third-party action (`m00nl1ght-dev/steam-workshop-deploy` v4), which would hold the Steam login;

    - (g) a new CI workflow on `main`. That is a larger change the user did not ask for.
- Decision: (a), the user's words; (c), Nadir's rule that no third-party action sees a secret, and the same image and login layout as the action (V320); (f). The user accepted it as written (2026-11-23, "Accept ADR-034").
  - The `Makefile` checks:
    - that the tag is `v` and HEAD's workspace version;
    - that HEAD's `deploy/` holds a plain build;
    - that HEAD is on the remote's `main`;
    - that the remote lacks the tag.
    - Then it tags and pushes the tag, or with `DRY_RUN=1` only prints those two commands.
  - The workflow runs `gate`, then `check` (fmt, both clippy lints, the native tests, and `deploy/` booted in the sandbox), then `crates`, then `release` and `workshop`, each publishing job in its own environment that only `v*` tags may use.

  - The release's checks are a subset of `npm run check`, which stays the gate before a tag.

The Workshop step, with a stub `steamcmd`, wrote the expected `item.vdf`, read back the new id, refused a non-numeric id, and removed the login file. The notes script summed the three files.

## ADR-035 Safe-mode triggers: when the bot spends a safe mode, and for whom: Accepted (2026-11-23)
- Context: ROADMAP P7.4 and SPEC §3.6 ask for safe-mode triggers. Safe mode (`StructureController.activateSafeMode`) stops every other user's creep, NPC invaders included, from attacking, dismantling, healing, or withdrawing anything in the room for `SAFE_MODE_DURATION` (20000) ticks, while the owner's creeps and towers act as usual (V280, V281, V300, V330, V331). It is scarce:
  - A room gains one activation per controller level reached (V188, V334), and more cost `SAFE_MODE_COST` (1000) ghodium each (P9's labs).
  - An activation starts a `SAFE_MODE_COOLDOWN` (50000) cooldown in that room, and only one of a player's rooms may be in safe mode at a time (ERR_BUSY, V325).
  - It cannot be activated while `upgradeBlocked` is set. One hostile `attackController` sets that for `CONTROLLER_ATTACK_BLOCKED_UPGRADE` (1000) ticks (V329). This is how attackers usually switch safe mode off before the real attack.
  - The activation is applied after the tick's intents, so hostile damage in its own tick still lands, and a hostile `attackController` in that tick cancels it, with no charge spent (V326, V328).
- Options asked (2026-11-23, with the facts above). "Core" is the room's spawns, towers, storage, and terminal; every option looks one step beyond a hostile's reach, since damage on the activation tick still lands:
  - The trigger: (a) the combat sim says a core structure falls before the towers kill the hostiles that can reach it, and at once with no tower; (b) the towers cannot kill every hostile in reach within a set number of ticks, ignoring the structures' hits; (c) any dangerous hostile one step from a core structure, whatever the towers can do.
  - CLAIM creeps: (d) a hostile with CLAIM parts within 2 tiles of the controller that the towers do not kill first; (e) the same, only while another dangerous hostile is in the room; (f) never.
  - Owners: (g) every owner, since the NPC username "Invader" is only community-sourced (V335) and the tower test already spares raids the towers win; (h) players only, skipping the owner name "Invader".
- Decision: (a), (d), and (g), the user's choices ("Core falls first", "Yes, if towers miss", "Count every owner").
- What it does (`rustedscreep_core::defense::safe_mode`, Critical, in each owned room with a dangerous hostile this tick):
  - **Can it be activated?** The snapshot reads the controller's `safeMode`, `safeModeAvailable`, and `safeModeCooldown` (V327) on each tick a hostile creep stands in the room. The bot then mirrors the game side's checks in their order (V325): charges left, no cooldown, not upgrade-blocked, the downgrade timer at least `CONTROLLER_DOWNGRADE[level] / 2 - CONTROLLER_DOWNGRADE_SAFEMODE_THRESHOLD`, and no own room known to be in safe mode.
  - **Core falls first (a).** Each dangerous hostile's damage a tick on a core structure is the larger of its melee `attack` and its `dismantle` within range 1 plus `defense.safe_mode_lead`, plus its `rangedAttack` within range 3 plus the lead. `dismantle` blocks `attack` on the same creep and neither blocks `rangedAttack` (V44); the powers are V288's.
    - The towers' time K is the sum, over those hostiles, of each one's kill time by P7.2's sim (every tower with energy for a shot, every hostile healer within range 3 at its most), so they are killed one after another and all of them hit until the last dies.
    - K is never when the sim kills one of them only after `defense.max_kill_ticks` or not at all, when the towers distrust it (the shot check), or when no tower can fire.
    - The structure falls first when K is never, or when the summed damage a tick times K reaches its hits, read this tick.
  - **CLAIM creeps (d).** A hostile with a live CLAIM part at Chebyshev range r of at most 1 plus the lead from the controller triggers when the sim's kill time k is never or at least max(r, 2). Its first hit can come on tick r - 1 from now, and a hit in the same tick as its death still lands. An activation protects from the next tick on, so it helps only when the creep could still hit on a later tick. k counts only the towers this tick's plan fires at the creep: the towers keep one focus across the room (P7.2), so towers that could kill it alone may be shooting another hostile, and the first hit is the loss.
  - **Every owner (g).** No owner's name is read for the decision.
  - **One call per room per threat, and one room a tick.** The bot calls `activateSafeMode` once in a room for each open threat (P7.1's threat). A refused call is free (V325), but the reasons the game gives last thousands of ticks, so it is not repeated. An accepted call may still not take effect: on the tick a cooldown ends the game side reads none while the processor still refuses (V338), and a same-tick hostile `attackController` cancels it (V326). Neither spends an activation. So when the next read shows no safe mode and the same activations left, the room calls again, as after a call that threw, up to `defense.safe_mode_calls` (3) calls in a threat. Only one room may be in safe mode, so of two rooms that trigger on the same tick only the first judged (in room order) is called. The one-room rule counts a room only when the snapshot has read it in safe mode: an accepted call is not counted until then, since a hostile `attackController` in its tick cancels it (V326).
  - **Log lines.** The call's outcome, with the reason, at warn ("activation accepted", confirmed by the next read's "is in safe mode" line, or "did not take effect"). A trigger the room cannot meet, with the reason it cannot, once per threat at warn. The room's own safe mode during a threat, once at info.
  - **The towers in the bot's own safe mode.** Hostiles cannot heal there (V300, V330), so P7.2's sim counts no hostile heal in such a room.
  - **Config.** `defense.safe_mode` turns it off. `defense.safe_mode_lead` (1 tile) is the step beyond reach; a creep moves at most one tile a tick. `defense.safe_mode_calls` (3) bounds the calls in a threat.
- Consequences:
  - One heavy invader beside a tower can trigger it. For example, 20 unboosted ATTACK parts deal 600 a tick, so a 5-tick kill deals 3000, a tower's `TOWER_HITS`. The same creep beside a spawn (`SPAWN_HITS` 5000) does not trigger it.
  - A creep that only walks past at the lead's distance counts as if it hits. The rule fires a tick early rather than a tick late.
  - Nothing is persisted. A global reset forgets which threats were tried, so a threat open across a reset may see one more call.
  - The snapshot's cost during a threat: 3 controller getters per room on ticks with a hostile in the room, and `hits` for each core structure (1 call each) on those ticks while `defense.safe_mode` is on and the room is not in its safe mode. Nothing on other ticks. Once a room's call is made or its line is out for a threat, its triggers are not judged again while its state allows nothing new.
- Risks:
  - The towers' real focus may differ from the sim's assumption (they choose dangerous, then the fewest ticks, across the whole room), so a far hostile they shoot first can leave a core structure under fire longer than K. Amendment 1 counts the focus they hold this tick; one they take after it is counted on that tick's re-check.
  - Ramparts over a core structure are not counted (their hits are read only every `upkeep.read_ticks`), so such a structure looks weaker than it is. That errs toward activating.
  - Power creeps and nukes are not read. A nuke ends safe mode at once (V332).
  - The activation tick's timing is inferred from the processor's order (V328).
  - The lead ignores walls and ramparts (the combat-math audit's M1). A ranged hostile parked just outside the line, at range 4 of a core structure, counts its `rangedAttack` though it cannot step closer while the line stands. With heal that holds the towers (K never), that fires at once and spends a charge. A fix needs the room's cost grid or the plan's line in the triggers; it is left for P7.5, whose defenders need the line's reach too.
  - K can be too low: the towers' shots are not debited across the summed kills, their spare shots may go to heals, and inactive or disrupted towers count at full power (V291, V299). Each tick's re-check limits the harm: a trigger one tick late still saves a structure the hostiles needed two or more ticks to break.
  - A creep with HEAL and ATTACK or WORK parts is counted as healing and hitting in the same tick, though `heal` blocks `attack` and `dismantle` (V44). This only makes the trigger fire sooner.
  - In a room with no tower (RCL1 and RCL2, or a new colony before its tower), any dangerous hostile one step from reach of a spawn fires at once, whatever its damage.
- Evidence: V325 to V338 (screeps-verifier, engine a90d26f, docs.screeps.com, crate 0.23.5); the native tests in TEST_PLAN §1 (Safe mode) and §7.
- **Amendment 1 (2026-11-24): the core trigger waits for the towers' focus out of reach** (the P7 gate's combat-math audit, its one high finding; the user's "Fix the trigger").
  - The problem: the towers keep a dangerous focus they kill within `defense.max_kill_ticks` until it dies (P7.2), and spare towers take other targets only when the focus dies in one tick. K assumed every tower fires at each hostile in reach. So a hostile in reach that the towers would kill in one tick, but do not shoot, gave K = 1, and the trigger fired only when its damage a tick reached the structure's hits: on the tick the structure fell, too late, since an activation protects only from the next tick (V328). The risk above named the mismatch, and "a trigger one tick late still saves a structure the hostiles needed two or more ticks to break" did not hold here. P7.5's defenders did not cover it either, since the towers alone kill such a hostile in one tick. Example: one tower holds a tank of 1 RANGED_ATTACK, 40 HEAL, and 8 MOVE parts, 41 ticks to kill, out of the spawn's reach, when a dismantler of 3 WORK and 3 MOVE parts breaks the spawn's `SPAWN_HITS` at 3 × `DISMANTLE_POWER` a tick in 34 ticks.
  - The fix: when no tower fires at any hostile in reach of the structure this tick, K adds first the sim's ticks to kill the towers' focus (`TowerControl::focus_kill`: the creep and its kill time, the defenders in range counted). Every hostile in reach but the focus is killed after it, so their kill times leave out its heal (`kill_of` with the healers but the focus), whether the focus is in reach or not. The order's reason carries the wait as `wait`, and the log line adds ", the first W on their focus out of reach". A tower firing at a hostile in reach means no wait: it is the focus, or a spare tower's one-tick kill when the focus dies in one tick (P7.2's `split`).
  - Why it is enough: the trigger is judged again each tick, so it only needs K of at least 2 on every tick the hostiles in reach outlive. Then a tick with no call has hits above 2D (D the hostiles' damage a tick), the next tick starts above D, and a call then still lands before the structure falls (the activation's own tick's damage included). With the wait, a focus out of reach gives K of at least 2 (its ticks plus at least one kill); with no wait, a tower fires at a hostile in reach, as before the amendment. When the focus dies the towers choose the next target, and that tick's K counts it. This assumes D does not rise between ticks: the lead covers a hostile stepping closer, but not one healed back to damage parts it had lost (a live part count follows the hits, V283), nor a harmless one that becomes dangerous that way. It also rests on V328's timing (inferred).
  - What the audits of the fix changed (2026-11-24, neither found a high): the focus's heal on the hostiles in reach was first counted as well as the wait, so a healer the towers shoot first (the attacker and healer pair) counted twice and spent a safe mode on a structure that holds (a medium); a spare tower's one-tick kill in reach first still waited a tick (a low); and, from P7.4, a dangerous healer the towers focus in reach still healed its partner in the partner's kill time, which made K long or never (a medium). All three are fixed, with a test each.
  - Costs: a safe mode is spent in such a fight where none was before, which is the point. The other choice, towers that break a kept focus for a hostile about to break a core structure, was not taken (the user's choice).
  - Risks left (lows of the same audits): `focus_kill` answers only when the towers' plan ran for the room this tick. A stop at the Critical tier's cap skips the safe-mode job on that tick too, but a fault in the towers' plan leaves the wait at 0, the bound before the amendment, though no tower fires that tick (its faults are unreachable by construction). Two one-tick kills in reach on the same tick are summed (K = 2 where both die this tick), so a structure with hits between D and 2D can spend a safe mode. A kill after the wait starts from the hostile's hits now, though it is healed while unshot. With defenders in range of a focus in reach, the towers may fire fewer towers and count on them, while the trigger counts every tower.
  - Evidence: `safe_mode_tests::scenario_core_falls_while_the_towers_keep_another_focus`, `scenario_a_healer_shot_first_counts_once`, `scenario_a_spare_tower_kills_in_reach_this_tick`, and `scenario_a_dangerous_healer_focus_in_reach_counts_once` (TEST_PLAN §7), each failing without its part of the fix (run this session).

## ADR-036 Scaled defenders: when a room spawns them, their body, their priority, and how many: Accepted (2026-11-24)
- Context: ROADMAP P7.5 and SPEC §3.6 ask for scaled defenders (creeps that fight hostile creeps in the bot's rooms, sized to the threat). The towers already fire whenever P7.2's combat sim says they kill a hostile within `defense.max_kill_ticks` (50), and hold fire against heal they cannot beat. E7N57 is at RCL6 with 2 towers and 2300 energy capacity, and its rampart line is 5 rampart gates and 32 walls (ADR-033). Facts behind the options:
  - Melee (`attack`, range 1) deals `ATTACK_POWER` (30) a part; ranged (`rangedAttack`, range 3) deals `RANGED_ATTACK_POWER` (10) a part (V288, V339). At 2300 energy a body of 17 ATTACK and 17 MOVE deals 510 a tick, and one of 11 RANGED_ATTACK and 11 MOVE deals 110.
  - A hit aimed at a creep on an own rampart lands on the rampart, and a melee attacker on a rampart takes no hit back (V243, V288, V340).
  - A move is checked only against its destination tile (V244), so a tile inside a closed line never touches a walkable tile outside it. So melee cannot reach over a wall, while a ranged creep reaches 3 tiles.
  - The game accepts an own creep as a `rangedAttack` target and the processor damages it (V339, V340).
- Options asked (2026-11-24, with the facts above):
  - When: (a) only when the towers cannot win: a dangerous hostile the sim does not kill within `defense.max_kill_ticks`, one the towers distrust (their shot check), or one in a room with no tower holding energy for a shot; (b) for every dangerous threat.
  - Body: (c) ranged, MOVE and RANGED_ATTACK, fighting from inside the line or a rampart; (d) melee on ramparts, ATTACK and MOVE; (e) both, chosen by where the hostiles stand.
  - Priority: (f) above every role but the zero-creep recovery worker; (g) above everything; (h) after the miners and haulers.
  - Scale: (i) full-capacity bodies, as few as the sim says kill the threat within `defense.max_kill_ticks` with the towers, up to a cap (3), and none for a hostile beyond the cap (logged); (j) as (i), but the cap anyway when outmatched; (k) one full body a threat.
- Decision: (a), (c), (f), and (i), the user's choices ("Towers can't win", "Ranged", "Above all but recovery", "Sim-sized team").
- What it does (`rustedscreep_core::defense::defenders`, Critical, in each owned room with a dangerous hostile this tick):
  - **Reach.** A defender never leaves the line. The tiles inside it come from a flood from the room's spawns over the movement grid's walkable tiles, taking in own ramparts but not passing them. A line with a gap lets the flood out, so the whole room counts as inside; a room with no spawn, or with no movement grid yet (no own creep has stood there lately), counts every hostile as in reach. A hostile is in reach when an inside tile lies within range 3 of it.
  - **When (a).** For each dangerous hostile in reach, the towers' sim (every tower with energy for a shot, every hostile healer within range 3 at its most, none in the bot's own safe mode) decides whether the towers alone kill it within `defense.max_kill_ticks`. A distrusted hostile counts with no tower.
  - **How many (i).** For each hostile the towers do not win alone, a binary search finds the fewest RANGED_ATTACK parts that, firing with the towers each tick, kill it within `defense.max_kill_ticks` by the sim. The room needs the most of these, and keeps the most it needed since its threat started. While the room's living defenders (a spawning one at its full body) hold fewer parts and fewer than `defense.max_defenders` (3) live, it requests the missing full bodies. A hostile beyond the cap gets no request and one warn line a threat.
  - **Body (c).** MOVE then RANGED_ATTACK in equal numbers, the most whole pairs the serving room's capacity pays for (11 pairs, 2200 energy, at 2300), asked for exactly, so the request waits for that energy. The MOVE parts come first, since damage empties the first parts first (V283).
  - **Priority (f).** `PRIORITY_DEFENDER` 175: below the recovery worker (200), above a worker under its room's minimum (150), the miners (125), haulers (115), upgraders (110), and every remote role.
  - **Fire.** The room's target is the towers' focus when the defenders can reach it, else last tick's target while it stays in reach, dangerous, and killable with the team, else the reachable dangerous hostile the sim kills soonest with the towers and the whole team. The towers' sim counts each defender in its home within range 3 of a candidate as firing at it (P7.2's `TowerControl::set_allies`), so the towers fire at a hostile they kill together with the defenders. So that count holds for the shot check, a defender in its home shoots the towers' focus first whenever it stands in range of it, even a harmless one such as a healer left after its attacker died; else the room's target in range; else the dangerous hostile within its reach with the fewest hits. The towers fire as many towers at a creep with a CLAIM part as they would alone (all of them when the kill needs the defenders), since P7.4's claim trigger counts only the towers firing at it (the combat-math audit's H2: otherwise it could spend a safe mode on a creep this tick's plan kills).
  - **Posts.** Within range 3 of the target, inside, free of hostiles, of other defenders, and of their posts this tick, preferring in order: out of melee reach (no hostile with an ATTACK part within 2 tiles), an own rampart, the nearest, the farthest from the target. A defender keeps its last post while it stays free, in range, and out of melee reach, so its move's goal stays the same.
  - **No friendly fire.** The intent buffer refuses a `rangedAttack` on an own creep (`Rejected::WrongTarget`).
  - **Idle.** A defender outside its home walks home; one with no reachable target holds and gives way. With no hostile in any owned room and every defender home, they all give way outside the scheduler's jobs. Defenders are not recycled.
  - **Config.** `defense.defenders` (on) turns the requests off; `defense.max_defenders` (3) caps the team.
- Consequences:
  - No energy goes on raids the towers win alone. At E7N57's 2 towers, an unboosted raid needs heal near the towers' damage before a defender spawns.
  - A full team at 2300 capacity costs 6600 energy and 66 ticks of spawn time a body (`CREEP_SPAWN_TIME` 3 a part), and the spawn's other requests wait meanwhile.
  - Ranged defenders deal a fifth of melee's damage for the energy, and enemy ranged attackers can hit them back. In return they reach over the walls anywhere along the line.
  - The snapshot reads each defender's `body` once in its life and skips its energy store. Own creeps' `hits` are still read only in rooms with an open threat and a tower, so a defender in a room with no tower counts at its whole body (no tower's sim counts it there).
- Risks:
  - The sim takes the hostiles where they stand this tick. A team sized at one range may be short when the hostiles move, and the need only grows within a threat.
  - A defender out of range of the towers' focus still counts for other candidates in the towers' sim, so the towers' choice among several hostiles may assume a defender's shot that goes to the focus instead.
  - The towers' expected hits for the shot check include the defenders' shots. A defender's shot the game refuses (V339) leaves the target above the expectation; `defense.miss_ticks` (3) such ticks in a row would make the towers distrust it.
  - The line's ramparts are held at 1% of their level's hits (ADR-032), so a rampart post is not preferred next to a melee hostile.
  - Players are not told apart from NPC invaders, and there is no ally list yet: `.claude/rules/combat.md` asks for a whitelist check at target selection and before every attack intent, which P10's whitelist adds. `rangedAttack` is the bot's first creep attack; it fires, as the towers do, at every hostile creep in an owned room (the user has no allies on shard3, 2026-11-23).
  - Critical work stops only at the tick's ceiling (ADR-013). A `defender work` unit skipped there, after the towers counted its shot, leaves the focus above the towers' expectation for that tick.
  - A defender with no target holds where it stands. One left outside the line (shoved off a gate, or stopped short on the walk home) stays there until the next threat gives it a post.
  - The team's size assumes every part fires each tick, but posts are limited to the free inside tiles within range 3 of the target; at a narrow gate fewer bodies may fire than were sized.
  - V244 is `inferred`, and its wording about diagonal barriers needs a raw re-read of `movement.js`. The flood does not depend on it: it steps in all 8 directions, so a diagonal gap in a line floods the whole room.
- Evidence: V339 to V341 (screeps-verifier, engine a90d26f, crate 0.23.5), with V243, V244, V283, V287, V288 and V340; the native tests in TEST_PLAN §1 (Defenders) and §7; `node js/tools/defense-sim.mjs`.

## ADR-037 Remote defenders: when a home fights for a remote room, the body, the size, and the priority: Accepted (2026-11-24)
- Context: ROADMAP P7.6 and SPEC §3.6 ask for remote evacuation. P6.3 already evacuates: hostile creeps with an active ATTACK or RANGED_ATTACK part in a mined remote room (one the bot mines without owning it) send its creeps home for `remote.evacuate_ticks` (1500) after the last sight, and its hooks `Remotes::threats`, `evacuate` and `clear_threat` were left for P7. An evacuated room is unseen, so the wait never ends early. Facts behind the options:
  - Raids are made by the private server's backend, a proxy for the MMO's closed one (V342): after about `INVADERS_ENERGY_GOAL` (100000) energy mined in the room. A reserved remote room can be raided (V346). Its controller level is 0, so its raids get the small 10-part bodies, usually one creep, the first a melee one of 2 TOUGH, 5 MOVE, 1 RANGED_ATTACK, 1 WORK and 1 ATTACK (V344, V345).
  - An invader lives at most `CREEP_LIFE_TIME` (1500) ticks, so ending the wait at its death saves little: it is seen at the exit where it appears (V343).
  - A reserved source makes 10 energy a tick (3000 every 300), so a 1500-tick wait in a two-source room loses up to 30000 energy, about a third of the room's income at one raid per 100000 mined.
  - Melee invaders chase the nearest creep by path and never flee; ranged ones step back from a creep within 2 tiles and hold at 3; `shootAtWill` is one `rangedAttack`; healers heal the most damaged of their own within 3 and follow the fighters; none leaves its room (V347 to V353).
  - A creep may `heal` itself, and `heal` does not block `rangedAttack` (V354 to V356).
- Options asked (2026-11-24, with the facts above):
  - Response: (a) fight when a two-sided combat sim says the defenders win and they cost less than the wait would lose, players and NPC invaders alike, the creeps still waiting during the fight; (b) the same, NPC invaders only (their owner's name is not verified, V272); (c) no fighting, the wait ending at the hostiles' death (`ticksToLive`); (d) keep P6.3 as it is.
  - Body: (e) RANGED_ATTACK, HEAL and MOVE; (f) P7.5's MOVE and RANGED_ATTACK; (g) ATTACK, HEAL and MOVE.
  - Size: (h) the cheapest body, and count up to 2, that wins within `defense.max_kill_ticks` and survives with a margin; (i) full-capacity bodies.
  - Priority: (j) 95, above every remote role, below the home's own workers; (k) the home defenders' 175.
- Decision: (a), (e), (h) and (j), the user's choices ("Fight when the sim wins", "Ranged + heal", "Smallest that wins", "Above remote roles").
- What it does (`rustedscreep_core::defense::remote`):
  - **The sim (`duel`, `fit`).** Stand and trade, erring on the bot's side: every defender's live RANGED_ATTACK parts hit the armed foe with the fewest effective hits (through boosted TOUGH, V287); every live foe with HEAL parts heals it as if adjacent; every armed foe alive at the tick's start hits every defender with its melee and ranged damage both, as if always in reach, and each defender heals itself after the damage and must stay above its floor alone, so the answer holds whichever one the foes pick (`shootAtWill`'s pick among several is not verified, V351). A defender's floor: it may lose `defense.remote_loss_pct` (40) of its hits, at most its MOVE parts' hits. Its MOVE parts come first and damage takes the first parts first (V283), so above the floor every RANGED_ATTACK and HEAL part is whole and the sim's damage and heal hold. The fight is won when every armed foe dies within `defense.max_kill_ticks` (50). `fit` leaves out the first defender to fall and judges the rest again, until they win or none is left.
  - **The size (h).** The cheapest team that wins against the foes whole (their healers refill them while the team spawns and walks, V352): the living defenders of the room first, every one counting toward `defense.max_remote_defenders` (2), then bodies of one shape within the home's capacity, all of which must go in; least energy, then fewest bodies, then fewest parts. For each HEAL count the least RANGED_ATTACK count is a binary search (more parts never lose a fight fewer won). The search runs only while the Standard tier does and only when the foes' or the team's bodies change (not their hits), as a heavy unit.
  - **When (a).** For each room in `Remotes::threats`, from its armed hostiles and healers as last seen: the snapshot reads every hostile's body once and its `hits` each tick in a mined room that holds an armed hostile. No request when the living defenders win alone (one info line), when the cheapest team costs at least the room's net energy (`RemoteProfit::net`, per creep life) over the wait left less the team's spawn and kill time (one warn line), or when no team within the cap wins (one warn line). Requests only while the Standard tier runs, as remote mining's.
  - **Body (e).** MOVE parts as many as the others (one tile a tick on plains), then RANGED_ATTACK, HEAL last, asked for exactly at the home's capacity. Against the usual raid (the small melee invader) at 1300, 1800 or 2300 capacity this is 2 RANGED_ATTACK, 3 HEAL and 5 MOVE, 1300 energy, killing it in 50 ticks by the sim; an RCL3 home (800) cannot field a winning team and waits.
  - **Priority (j).** `PRIORITY_REMOTE_DEFENDER` 95: above the remote miner (90), below the home's own workers (100).
  - **Together or not at all.** Bodies spawn one after another, but the sim has the whole team fight from the first tick, so each tick the room's ready defenders (out of the spawn, above their floor) are judged by `fit` at their hits against the foes as last seen: those it keeps go in, the others, and all of them while none win, wait in the home (one in the room walks out). Invaders cannot leave their room (V353). A defender at or below its floor leaves, heals itself, and does not count in the team.
  - **In the room.** One target for the room (the armed foe with the fewest effective hits, kept while it lives), so the team never splits its fire; `rangedAttack` on it within range 3, else on the armed foe within 3 with the fewest hits; a self `heal` when damaged or when a foe can hit it this tick (a ranged one within 3, a melee one adjacent: attacks are checked against the tick's starting positions); a post within 3 of the target, off the edge, more than 2 tiles from any foe with a live ATTACK part, kept while valid. The work is Critical, as the home defenders' (a defender in a fight heals and shoots every tick, as the sim has it).
  - **The wait's end.** When a remote defender of the room stands in it and sees no armed hostile, the threat ends (`Remotes::clear_threat`) and the miners and haulers go back. The defender then guards the room, off the edge tiles, for the rest of its life, and the next raid is sized with it first; a guard whose room is no longer mined walks home and waits there.
  - **Name and role.** `Role::RemoteDefender`, code `p`, a remote role whose name carries its remote room (`pE7N57E8N57-…`), an additive change to the persisted name format. The remote manager does not drive it.
  - **Config.** `defense.remote_defenders` (on), `defense.max_remote_defenders` (2), `defense.remote_loss_pct` (40, 10 to 50).
- Added in the implementation, not asked:
  - Only a remote defender in the room ends the wait: evacuating creeps that still see the room when a hostile steps out do not, so a player who steps in and out over the edge does not pull the crew back into reach. With no defender, P6.3's wait stands.
  - A threat a defender ended does not count toward `remote.contest_threats` (3 within 20000 ticks abandons a room, P6.3): at one raid about every 5000 ticks, a defended two-source room would otherwise be abandoned for raids it won.
  - The owned rooms' threat assessment (P7.1) skips the remote rooms' hostiles, so no tower, safe mode or home defender acts on them, and the towers' shot check (P7.2) skips a target that left the room for a remote one, where it is assessed too.
  - From the combat-math audit (applied: H1, every defender takes every foe's damage; H2, the team goes in together; M1, one target a room; M2, the foes sized whole; M3, the work Critical; M4, a retreat at the floor; the spawn and kill time out of `pays`; every member against the cap) and the hot-path review (applied: the sizing keyed on bodies, not hits, run only while Standard runs and as a heavy unit; a self heal only against a foe that can hit this tick; the room's hostiles read once a tick; the unboosted damage without `damage_taken`; the guard of a room no longer mined sent home).
- Consequences:
  - A typical raid costs 1300 energy of defender, once, against up to 30000 energy of waiting; the guard then answers the next raids in its life for nothing more.
  - Each armed hostile in a mined room adds a `hits` read each tick and a body read once (3N + 2 calls); each remote defender adds a `hits` read each tick and a body read once, and skips the store read. A fighting defender issues up to three intents a tick (`heal`, `rangedAttack`, a move).
  - The crew still walks home and back for each raid, as the user chose.
- Risks:
  - The sim takes the posts' safety for granted: it lets melee land every tick, which covers a defender that does not reach its post, but a team sized at the limit (the 1300-energy answer to the usual raid takes all 50 ticks) has no time in hand. Raising the margin means a lower `remote_loss_pct` or a shorter `max_kill_ticks`, both of which also govern other fights.
  - The invader facts are the private server's (V342 to V346, `inferred` for the MMO); the sizing reads the bodies it sees, so it does not depend on them, but the costs in the consequences do.
  - The foes are kept as last seen: a raid that grows while the room is unseen is met by a team sized for the smaller one, and a second line goes out only when the defender sees it.
  - A remote defender spawning when its room's state is lost (a global reset) is not counted until it is out of its spawn, so a reset during a threat can order one more.
  - There is no ally list yet (P10): the defenders fire at every armed hostile in the room, players included (the user has no allies on shard3, 2026-11-23).
  - A post moves when the target or a melee foe does, and each new post is a flow field to build (heavy), so a chase rebuilds one each tick per defender (as P7.5's defenders do); a defender already on its post builds none.
  - A player creep whose weapons sit at the front of its body is disarmed by damage before it dies; the room then reads clear and the wait ends while it lives, and a healer could refit it (invader bodies keep their weapons at the back, V344). The walk into the room is not counted in `pays`.
  - No remote room is mined live today (ADR-031), so no live evidence is possible until one is.
- Evidence: V342 to V357 (screeps-verifier, engine a90d26f, backend-local master, crate 0.23.5), with V44, V283, V287, V288 and V339; the native tests in TEST_PLAN §1 (Remote defenders) and §7; `node js/tools/remote-sim.mjs`'s check 7.

- Context: ROADMAP P8.1 and SPEC §3.7 ask for scouting and observers, so that P8.2's claim scoring (choosing the next room to own) has intel on the rooms around each home. Three things already look at rooms, and none keeps what claim scoring needs.

  - **ADR-030's signer** tours every room that can have a controller within `sign.max_distance` (31) of a home, nearest first, and persists a record. But it keeps only the sign and the other owner's towers, and a signed room is not due again for `sign.recheck_ticks` (100000).
  - **The snapshot** already walks every visible room each tick (its name, controller, and hostile creeps), whoever gives the vision.
  - **Vision facts** (VERIFICATION_LOG V358 to V363): an observer exists only at RCL8 (V234; E7N57 is RCL5). `observeRoom` reaches rooms within `OBSERVER_RANGE` (10) on both world axes, a square with no wrap, or any room under the power effect `PWR_OPERATE_OBSERVER`. A call on tick T gives full vision of the room, as a creep there would, on tick T+1 only. A second call in the same tick replaces the first and is not billed again (V34). The crate's `observe_room` unwraps an unknown return code (V366), so the glue binds the call itself, as the towers' calls are.
- Options asked (2026-11-25, with the facts above):
  - Who looks: (a) a new explorer role, one for the bot, one MOVE part (50 energy), in the Optional tier, touring the rooms near the homes whose intel is missing or stale, nearest first, avoiding rooms with seen towers; (b) the signer also explores (ADR-030 amended: rooms with stale intel become due as looks), so scouting stops whenever `sign.enabled` is off; (c) no new creep: the reads any creep's vision gives, and the observers. In every option, any vision of a stale room updates its record for free.
  - Persistence: (d) a segment record (ADR-004's versioned, checksummed frame, a new owner, schema 1), written when it changes, at most once per `scout.save_ticks`; (e) the heap only, so every push forgets it and the explorer tours again.
  - Observers: (f) now, with a planner gate of their own (`planner.observer`, on), split from `planner.late`, and a loop that observes the stalest room in range on Optional ticks; (g) later, with P9's late structures.
  - Reach: (h) 10 rooms (`OBSERVER_RANGE`, so the explorer and a later observer cover one square); (i) 5 rooms.
- Decision: (a), (d), (f) and (h), the user's choices ("New explorer role", "Segment record", "Now, own gate", "10 rooms").
- What it does (`rustedscreep_core::expansion`):
  - **The atlas.** One record per room that can have a controller (`economy::is_remote_room`, V231) and that the bot does not own: the tick it was seen; its room status (normal, closed, novice, or respawn, from `Game.map.getRoomStatus`, V168); its controller's owner class, level, and tile; who reserves it and until when; another owner's safe mode and until when; its sources' tiles; its mineral's type, tile, and density (V364); the other owners' towers and spawns, keeper lairs, and an invader core's level (V365); and the hostile creeps seen. A room the explorer cannot reach gets an entry marked unreachable with the tick, so it waits too.
  - **Reads.** The snapshot reads a visible room into the atlas when its record is missing or older than `scout.refresh_ticks`, at most `scout.max_reads` rooms a tick, and only once the record has loaded. Any vision counts: the signer's tours, the remote creeps, the explorer, and an observer's look.
  - **The explorer (a).** `Role::Explorer`, name code `x` (an additive change to the persisted name format), body one MOVE part. At most one for the bot. It is requested from the home nearest the nearest due room, while the Optional tier runs, at `PRIORITY_EXPLORER` (72), between the signer's 70 and the remote scout's 75. A room is due when it lies within `scout.max_distance` of a home at `scout.min_level`, can have a controller, and its record is missing or stale. The explorer walks to the due room nearest it, one route search a tick (as the signer's, with the same kind of limits), avoiding rooms where the atlas shows another owner's towers. A room it cannot route to is marked unreachable; one too far for its remaining life is passed over for that life. With nothing left, it calls `suicide` so the next one starts from a home. If it steps into a room with another owner's towers, it stays on the entrance's edge tile, and the engine carries it back out (V151), as the signer does.
  - **Observers (f).** `planner.observer` places the plan's observer at RCL8, apart from the other late structures. On each tick the Optional tier runs, each own observer in a room at a level that allows one looks at the stalest due room within `OBSERVER_RANGE` of its room that no other observer takes and that is not already visible. That is one billed intent, and none when nothing is due. Rooms with towers and unreachable rooms are included, since an observer risks nothing. The next tick's snapshot reads the room.
  - **The record (d).** Segment `PersistConfig::atlas_segment` (94), owner kind `ATLAS` (5), schema 1, 35 bytes a room with two sources (`expansion::entry_len`). Of the 441 rooms within 10 of one home, about 318 can have a controller (72 of a sector's 100), about 11 KB. When the rooms within reach of every home would not fit one segment, the oldest entries are left out of the write. Rooms farther than `scout.max_distance` from every home are dropped.
- Added in the implementation, not asked:
  - The explorer needs no record of its own: the atlas says what is due. Like the signer, it starts only once the record has loaded.
  - ADR-029's scout and its heap intel stay as they are. The remote manager does not read the atlas yet. Seeding it after a reset, which would save a 50-energy look, is left for later.
  - The `scout.observers` switch turns the observer loop off on its own. `scout.enabled` off stops the reads, the explorer, and the observers.
  - From the hot-path review (2026-11-25), applied:
    - Rooms the bot owns are never due, homes or not: a newly claimed room below `scout.min_level`, or one without a spawn, is not read by the snapshot and would otherwise hold the explorer there for good.
    - A look whose room is not visible on the next tick marks the room unreachable, so it waits `scout.refresh_ticks`. `observeRoom` accepts a room past the world's border by its name alone (V358), and the driver then has no room to give (V362); without the mark, every observer would look at it every tick.
    - The reads follow the last tick's tier: none unless it ran the Optional tier (the snapshot comes before this tick's budget), so a low bucket stops them with the rest of the Optional work.
    - An explorer away from a home whose nearest due room's route is longer than its life ends, so a fresh one starts from a home, instead of one far search a tick. A search that runs out of ops marks the room unreachable only from a home room.
    - A room an explorer died in is neither a target nor on a route for `scout.refresh_ticks` (heap only), so explorers do not die there one after another.
    - The atlas is pruned by the owned rooms, not the homes, so a home that loses its spawns keeps its rooms. Each look's billed cost counts against the Optional cap. The size warning is logged only when the rooms left out change. A decode reserves no more entries than the payload can hold.
- Consequences:
  - The atlas is P8.2's input: claim scoring reads it, and needs no vision of its own.
  - A touring explorer costs 50 energy and 3 ticks of spawn time per life, and about 0.2 CPU a tick for its move (one billed intent) while it walks. A first pass of the about 318 rooms that can have a controller takes about 11 lives at about 30 rooms a life. At `scout.refresh_ticks` (50000) it then idles about two thirds of the time.
  - A read costs about 25 JS calls (the controller's tile, reservation, and safe mode; the sources and mineral; four filtered `find` calls for towers, spawns, lairs, and cores; the room's status), once per room per refresh.
  - An observer costs one intent per tick while a room in range is due, about one look per 157 ticks once the square is fresh (318 rooms per 50000 ticks).
- Risks:
  - The explorer can still die to a tower it has not seen: one shot kills a one-MOVE creep (V285). It costs 50 energy, and the room's record is still made on the tick it enters.
  - The observer loop cannot run live until a room reaches RCL8. Until then it rests on the native tests and the sandbox sim.
  - The record grows with the number of homes. Past one segment, the oldest rooms go unrecorded across a reset and are toured again.
  - The status read is the room's status when seen. A novice area that opens (V168) stays recorded as novice until its next refresh.
- Evidence: V358 to V368 (screeps-verifier, engine a90d26f, driver cf63d8a, common 2fb779b, crate 0.23.5; the observer's game side, processor, and driver read byte-exact with curl), with V34, V101, V151, V168, V231, V234, V267, V285, and V337.

## ADR-040 The upload size: what keeps the code under the MMO's 2 MB cap: Accepted (2026-11-25; implemented 2026-11-25)
- Context: the game stores a player's code branch, every module together, under a size cap, and refuses an upload over it. The only figure for the MMO is the Dev Team's 2 MB from 2018, binary modules counted at their base64 size (V76, V371, both inferred); nothing newer states it (V370, unverified). The open-source server raised its own cap to 5 MB in 2019 (V369), which does not show the MMO did. So `npm run size` keeps `JSON.stringify(modules)` under 2097152 characters.
  - **Where it stands.** After P8.1 the upload is 2069314 of 2097152 (98.7%): main.js 103268 B and the wasm, 1472254 B, as 1963008 base64 characters in 3 text modules (ADR-015, the wasm as base64 text, since the GitHub link mangles binary files; ADR-028, the parts of at most 905709 bytes the link delivers intact, V257). P8.1 added about 93400 characters, and P7's modules between about 4000 and 77000 each. P8.2 to P12 are still to come, so the next module most likely does not fit.
  - **The boot today.** The loader decodes the base64 and checks the CRC-32 the build recorded before it compiles: 17.63 CPU for 1867328 characters on shard3 (the boot line of `d8db073590e8-7ba99bbd`). The same work takes 11.5 ms cold in Node 26 for 1963008 characters (this session), so shard3 runs this kind of JS about 1.5 to 1.6 times slower than Node 26 does (inferred from one sample).
  - **What the runtime offers.** No built-in decompression is known on the MMO (V373: the driver defines no `zlib` or `DecompressionStream`; inferred), and `atob` and `Buffer` are absent (V141). A loader that inflates ships its own decoder. The loader's rules allow its own code but no bundled runtime dependency (`.claude/rules/js-loader.md`).
- Measured this session (the P8.1 build; wasm-opt from binaryen version_133; DEFLATE is Node's zlib, raw, level 9):

  | Build | Wasm (B) | As base64 (chars) | DEFLATE (B) | DEFLATE as base64 (chars) |
  |---|---|---|---|---|
  | `opt-level = 3`, `wasm-opt -O4` (today) | 1472254 | 1963008 | 537865 | 717156 |
  | `wasm-opt -Oz` | 1457057 | 1942744 | 534348 | 712464 |
  | `opt-level = "s"`, `-O4` | 1086437 | 1448584 | 433946 | 578596 |
  | `opt-level = "z"`, `-O4` | 891320 | 1188428 | 367459 | 489948 |

  Brotli (quality 11) takes today's wasm to 409760 B (546348 characters), but a JS Brotli decoder carries a dictionary of about 120 KB, more than it saves over DEFLATE. A scratch DEFLATE decoder (zlib's `puff` design, table-driven, 3363 characters of source) rebuilt today's wasm byte for byte in 13 to 25 ms in Node 26, 22 ms on the first, cold run.
- Options:
  - (a) **Compress the wasm.** The build compresses the optimized wasm with DEFLATE before the base64 (Node's zlib, a build tool only), and the loader inflates it with a small decoder of its own in `js/src/` (no dependency), then checks the CRC-32 of the inflated wasm as it does today. Upload about 824000 characters with today's code (717156 for the wasm, main.js, about 3400 for the decoder): 39% of the cap, and the wasm fits one module. No change to the code that runs each tick. The boot gains the inflate, about 20 to 35 CPU once per global reset on shard3 (inferred from the Node timing and the ratio above), less what the shorter base64 saves. Tests: the decoder against zlib on random and real inputs in the tool tests, every sandbox sim booting the compressed form, and the boot line after the first push.
  - (b) **Smaller code.** Cargo's `opt-level = "s"` (26% smaller, upload about 74%) or `"z"` (39% smaller, about 62%). It slows the code that runs every tick, by an amount not measured here (a profiler build on the MMO would measure it), which the project's rule against trading performance for CPU savings weighs against; and the headroom it buys is a few modules.
  - (c) **`wasm-opt -Oz`.** 1% smaller. Not enough on its own.
  - (d) **Find the real cap.** Push a build padded past 2 MB and see whether it boots; if the MMO allows 5 MB, nothing else is needed for a long time. But what a refused upload leaves on the branch is not known (V372): the bot may keep the old code, or be left with none, and a 2 MB cap gains nothing.
  - (e) **A denser alphabet.** Text with 15 bits a character (base32768) instead of base64's 6, no decompression: about 785000 characters. But non-ASCII text through the GitHub link and the game's storage is not verified, and each such character takes 3 bytes of UTF-8, so the parts hit V257's per-file limit sooner.
- Decision: (a), the user's choice on 2026-11-25 ("Compress the wasm").
- Implementation (2026-11-25): `js/src/inflate.ts` (the decoder, about 200 lines, strict on every malformed stream), `loadWasm`'s inflate when the build records `inflatedBytes`, and the build's DEFLATE step (Node's zlib, raw, level 9, checked to inflate to the `.wasm`). Measured on the P8.1 code: the upload went from 2069314 to 833873 of 2097152 characters (39.8%), one text module of 717177 bytes, main.js 103268 to 113529 bytes (the decoder and its comments). One change the decision did not name: `npm run size` checked the larger of the binary and text uploads, and now checks the text upload only (the MMO's, through the GitHub link; no tool uploads the binary form since ADR-021), reporting the binary figure for information. Otherwise the binary form, 2079712 characters, would fail a budget that no upload of it meets.
- Recommendation: (a). It buys the most room (from 98.7% to about 39% today, and the compressed wasm grows by about a third of what the raw wasm does), costs nothing per tick, keeps every file ASCII and the CRC-32 check, and needs no live experiment. (b) stays possible later, measured with the profiler, if the code ever outgrows (a). (d) is the user's call at any time, since its risk is to the live bot.
- Consequences (with (a)):
  - Amends ADR-015 and ADR-028: the text modules carry the base64 of the DEFLATE stream, not of the wasm. The build records the compressed length, the wasm's length, and the wasm's CRC-32; the boot line names the form (`deflate`) and both lengths.
  - `npm run size` measures the upload as before; the module split stays for a stream that would pass 905709 bytes.
  - The sandbox's binary form (a `.wasm` module, ADR-015's fallback) stays uncompressed.
- Risks (with (a)):
  - A decoder bug inflates a wrong wasm: the CRC-32 check refuses it, the boot does not happen, and the loader backs off and notifies (ADR-003). The tool tests and the sandbox run it on every build before a stage.
  - The boot's cost on shard3 is an estimate until the first boot line shows it.
- Evidence: V76, V257, V369 to V373, V141; the boot line of `d8db073590e8-7ba99bbd` (STATUS 2026-11-24); this session's measurements above (`npm run size`, the scratch builds and timings in the session's scratchpad).

## ADR-041 Claim scoring: the plan check, live or pure, and one-source rooms: Accepted (2026-11-25; implemented 2026-11-25)
- Context: ROADMAP P8.2 and SPEC §3.7 ask for claim scoring: ranking the rooms near the homes so P8.3's claimers know which room to own next. P8.1's atlas (ADR-039) already holds what the bot last saw of each room within 10 of a home, kept across global resets, so the score needs no vision of its own.
  - **What a claimer can take** (V374 to V381, `claimController` read through extracted fetches): a controller at level 0 (any owner refuses it, the bot's own room included), not reserved by another user (the bot's own reservation is fine), not under another owner's safe mode, and not in a novice area once the bot owns `GCL_NOVICE` (3) rooms. GCL N allows N rooms (V378). Rooms of another status are walled off from a home (V168).
  - **What the base planner can tell.** P4's flood planner (ADR-007) plans a room with no standing spawn (the corpus's fresh mode: every one of the 72 shard3 rooms gets a valid plan), and its validator measures the plan: the walks from the hub to each source and to the controller, the ramparts, the first spawn's tile. A plan takes about 5 ms a room natively (the P4 gate's benches), about 9 steps; on shard3 likely 10 to 15 CPU (inferred, not measured). The terrain of any room can be read without vision (`Game.map.getRoomTerrain`, V156; 5 JS calls, V157).
  - **What CPU allows.** The free tier's 20 CPU (V35) is the binding limit: each owned room has a fixed cost in creeps and logic, and a remote room costs about 0.9 CPU a tick (P6.1's model).
- Options asked (2026-11-25, with the facts above):
  - The plan check: (a) plan the top 3 candidates with the base planner before choosing, so a room where no base fits is never claimed and the plan's walks and ramparts count; (b) the atlas only, with the room planned after its claim (a room with no fitting base can then waste a claim: 650 energy and a GCL slot).
  - Scope: (c) live now, the ranking in the Optional tier with a `rustedscreep.claims()` console view; (d) a pure model with tests only, as P6.1's profit model was, the glue coming with P8.3.
  - One-source rooms: (e) two sources required; (f) the score decides, a one-source room entering at half the sources term.
- Decision: (a), (c), and (f), the user's choices ("Plan the top 3", "Live ranking now", "Score decides").
- What it does (`rustedscreep_core::expansion::claim`, glue `rustedscreep-wasm` `claim.rs`):
  - **Candidates.** A room of the atlas that was read and not found unreachable, not owned by the bot (a claimed room stays neutral in the atlas, which reads no owned room), with a controller at level 0, no other user's reservation that has not ended, no invader core and no other user's towers or spawns, at least `claim.min_sources` (1) sources, and the status of a home within `claim.max_distance` (5) rooms; never a closed room, and never a novice room once the bot owns `GCL_NOVICE` rooms. The GCL is not a filter: the ranking holds whether or not a claim is allowed now (P8.4).
  - **The score,** in milli-energy a tick (me/t), each term from the constants or a `claim.*` weight: + the sources at `SOURCE_ENERGY_CAPACITY` / `ENERGY_REGEN_TIME` each; + the free neighbors' sources across the room's exits, at `claim.remote_pct` (30) percent of a reserved room's yield, for the best `remote.max_rooms` (2) of them (a neighbor counts only with no owner, no other user's reservation, towers, spawns or core, and no owned room across one of its exits); − `claim.distance_cost` (1000) a room to the nearest home; − for each room another player owns within `claim.threat_range` (2), `claim.foreign_cost` (4000) times its level over 8, once more for each room it is closer than the range's end; − from the plan, the haulers for each source's way to the hub and the yield's way to the controller (two CARRY parts and a MOVE part a load, renewed every `CREEP_LIFE_TIME`), and the repair of the ramparts' decay at `REPAIR_COST`; and the plan's closed sides drop their neighbors' remotes.
  - **The plan check (a).** Before its plan, a candidate's value is an upper bound, since the plan's terms only subtract. The ranking is sorted by value, and the first unplanned candidate is planned while fewer than `claim.plan_count` (3) planned ones rank above it, so once the top 3 are planned no unplanned room can beat them; the best is the first once it is planned. A plan reads the terrain from movement's cache or `Game.map.getRoomTerrain`, runs the flood planner with no standing spawn one phase a step, then its validator. A plan that fails or does not validate drops the room until its sources or controller read differently or the planner's tunables change; a room whose terrain cannot be read is left out until the next timed score. Outcomes are kept in the heap only, keyed on the controller, source, and mineral tiles.
  - **Live (c).** The Optional `claims` job, after scouting's work, runs only while the atlas holds a room and a score is due or a plan is wanted or running; each step is marked heavy. The ranking is rebuilt on every change to the atlas's facts (a new revision counter in `Scouting`), the owned rooms, or the claim config, and at least every `claim.score_ticks` (1000); each home's status is read (`Game.map.getRoomStatus`, one call a home) when the homes change or `claim.score_ticks` has passed. A log line names a new best room with its terms and first spawn; another names a room with no valid plan. `rustedscreep.claims()` shows the counts, why rooms were left out, the plan running, and the first 5 candidates.
- Added in the implementation, not asked:
  - The remotes term is capped at `remote.max_rooms` neighbors: on the terrain corpus, with every room taken as neutral, four neighbors gave remotes above the room's own sources (21 against 20 energy a tick), which no home mines at once.
  - A changed atlas triggers a score at once: with only `claim.score_ticks`, a room read just after a score waited up to 1000 ticks (the scouting sim showed it).
  - From the hot-path review (2026-11-25; no high), applied: the medium, a score on every read, since every read raised the atlas's revision and each score read every home's status: the revision now moves only when a read differs in more than its tick, and the homes' statuses are read again only when the homes change or `claim.score_ticks` has passed. The lows: a candidate the atlas no longer holds with a controller tile leaves the ranking when its plan would start (it could have been wanted every step); a room whose terrain read failed tries again at the next timed score instead of waiting for the next global; a changed `claim.*` config or `remote.max_rooms` makes a score due, and changed planner tunables (`planner.hub_clearance`, `planner.exposed_penalty`) drop every outcome so the rooms are planned again; the terrain moves into the plan without a copy, and the planner's scratch buffers are released once no plan is wanted. Left: during the observer's first sweep at RCL8 (or a tour of new rooms) each new room is a new fact, so a score runs on each tick that reads one (pure Rust over the atlas, no JS call while the homes are unchanged).
- Consequences:
  - P8.3's claimers take `Claims::best()`: the room, its home, and the first spawn's tile from the plan. P8.4 checks the GCL before a claim.
  - After each global reset the top rooms are planned again: about 9 steps a plan, 3 plans at least, more when upper bounds tie (9 plans, 81 steps on the all-neutral corpus).
  - Nothing is persisted, and no intent is issued.
- Risks:
  - Every weight but the energy terms is a guess (`remote_pct`, `distance_cost`, `foreign_cost`) until P8.3 claims a room and P6's carried reading (ADR-031) measures a remote one.
  - The atlas's reads are as old as `scout.refresh_ticks` (50000): an owner or reservation that came since shows only at the next read, and the claimer must check the room on arrival (P8.3).
  - The plan's CPU on shard3 is an estimate until a live run shows it.
- Evidence: V374 to V381 (screeps-verifier, engine a90d26f, common 2fb779b, crate 0.23.5), with V35, V156, V157, V168, V184, V266, V304; `tests/claim_corpus.rs` and `scout-sim.mjs` run C (STATUS 2026-11-25).

## ADR-042 Claimers and pioneers: who builds the claimed room, and how far a claim may reach: Accepted (2026-11-25; implemented 2026-11-25)
- Context: ROADMAP P8.3 and SPEC §3.7 ask for claimers (a creep with a CLAIM part that takes a room's controller) and pioneers (creeps sent to build up the newly claimed room until its own spawn stands). P8.2's claim scoring (ADR-041) already names the room to claim, its home, and the first spawn's tile from a plan that validates (`Claims::best`, `Fit::spawn`).
  - **What the code had already.** P5.1's global spawn queue serves an owned room with no spawn from the nearest room with a spawn within `spawn.help_range` (3): that room spawns the request's creep for it, but only on a tick it starts full and the Standard tier runs, and after its own requests. Movement walks a creep to a target in another room (P2.2). The opening (P2.4) runs in every owned room, spawn or not: its workers harvest, build the room's sites, and upgrade.
  - **The gap.** A room just claimed holds no energy (no spawn, no extension), and the opening sized a spawnless room's workers at the smaller of its own capacity and the helper's: 0, so no worker body fit and nothing was asked for. Nothing placed a spawn site in a room with no spawn (the base planner waits for one, P4.3).
  - **Reach.** Claim scoring's candidates reach `claim.max_distance` (5) rooms from a home, beyond the help range.
  - **Engine facts.** `claimController` needs a CLAIM part, range 1, a controller at level 0 with no other user's reservation, and fewer owned rooms than the GCL level (V374 to V378); a claimed room starts at level 1 (V377) with about 20000 ticks before it would downgrade (V384); a spawn site needs no name (V200); `Game.gcl.level` is the GCL (V379, V382).
- Options asked (2026-11-25, with the facts above):
  - The pioneers: (a) the claimed room's own opening workers, spawned by the nearest spawn room through P5.1's help (only from a full room, after its own requests), with the sizing fixed for a room with no capacity; (b) a new pioneer role from the claiming home, with its own count, body, and priority, spawned whether or not the home is full, until the first spawn stands.
  - The reach: (c) lower `claim.max_distance` to `spawn.help_range` (3), and the claimer refuses a room no spawn room can serve; (d) raise `spawn.help_range` to 5 for every helped request.
- Decision: (a) and (c), the user's choices ("Helped workers", "Claim within help range").
- What it does (`rustedscreep_core::expansion::claimer`, glue in `rustedscreep-wasm` `claim.rs`):
  - **The order.** On a tick the Optional tier runs, the Critical `claimer` job orders one claimer when `claim.claimers` is on, no claimer lives, every owned room has a spawn (one claim at a time), the best planned candidate is not waiting after a failed claim, the bot owns fewer rooms than `Game.gcl.level`, the candidate's home has a spawn at `claim.min_home_level` (4) or more, and a spawn room lies within `spawn.help_range` of the candidate. The GCL is read (3 reads through `Reflect`, so a world without `Game.gcl` reads none) only when every other check passes, at most every `claim.score_ticks`. The body is one CLAIM part and `MOVE_COST_SWAMP` / `MOVE_POWER` (5) MOVE parts, 850 energy, so it walks a tile a tick on any terrain; the priority is 78 (below the reserver's 80, above the remote scout's 75). Its name carries the room it claims (`Role::Claimer`, code `k`, a remote-style name), so neither a changed ranking nor a reset turns it.
  - **The claimer's work (Standard).** One route search a global, keeping out of rooms the atlas saw another owner's towers in (the explorer's limits); a route that does not fit its life less `scout.life_margin_ticks`, or none, fails the claim, as does a second move that finds no way after a search. Next to the controller it calls `claimController` once a tick. On the next tick the room is owned (it ends with `suicide`), or the call was refused: the room's atlas entry is marked stale (`Scouting::expire`), the claimer waits in the room until the snapshot reads it again (at most 10 ticks), so the ranking sees what the claim met, and then ends.
  - **Failures.** No route, a route too long, a refused call, or a claimer gone before its room is owned: the room waits `claim.retry_ticks` (5000) before another claimer goes. The list is in the heap.
  - **The pioneers.** The opening sizes the workers of a room whose own capacity pays for no worker at the serving room's capacity (`economy::worker_capacity`). A site waits `placement::APPEAR_TICKS` to appear; a refused tile is not tried again this global (the site cap passes).
- Added in the implementation, not asked:
  - The claimer's own room gets no remote read in the snapshot, only its controller as an object (`claim_rooms`): with the remote read, remote mining took the claimer's vision as intel and placed its container sites in the room being claimed (the scouting sim's run D showed it).
  - The spawn site's log line goes out in the act step, where the call returns, since the act step comes after the tick's log pass.
  - From the hot-path review (2026-11-25), applied: the high, a route found and then not walked (movement finds no way) searched again every tick of the claimer's life, since each search cleared the miss; a miss is now cleared only by a move that finds its way, so the second miss fails the claim. The medium, the owned rooms' spawns and spawn sites were scanned per room every tick: now one pass over the spawns, and the objects only while the claimers are on and a room has no spawn. The lows: the controller is pushed only in the claimer's own room; the claimer's store is not read (no CARRY part); after a refusal the claimer waits at most `REREAD_WAIT` (10) ticks for the read, not at all with scouting off, and its later end is no second failure; no route search is counted without a router.
- Consequences:

  - On shard3 the GCL is probably 1 (not read; the bot owns only E7N57, and GCL 2 needs 1000000 control points, V378), so no claimer would go until GCL 2; the GCL is read once every `claim.score_ticks` while E7N57 has a best candidate, and `rustedscreep.claims()` shows it.
  - Nothing is persisted. A reset forgets the failed claims (at most one more claimer each) and re-plans a claimed room that still has no spawn site.

P7.5's defenders are asked for any owned room with a dangerous hostile, so a full spawn room in range would serve the claimed room as it serves the pioneers, but their posts come from the rampart line, which a room with no spawn has no plan for: that case is untested.
  - A structure a former owner left can block the plan's spawn tile; the site is then refused and not tried again this global (logged).

## ADR-044 Mineral mining: where the minerals go, when a room mines, and who carries: Accepted (2026-11-25; implemented 2026-11-26)
- Context: ROADMAP P9.1 and SPEC §3.8 ask for minerals: each owned room's mineral mined and kept, for labs (P9.2), the factory (P9.3), terminal balancing (P9.4) and the market (P9.5).
  - **The live home.** E7N57 is at room controller level (RCL) 5. Its storage is not built: `planner.storage` is off (the user's choice, 2026-11-18). `CONTROLLER_STRUCTURES` allows the extractor (the structure a creep needs on a mineral to harvest it) and the terminal only from RCL6 (V393), so nothing can be mined there yet.
  - **The planner.** It already plans the extractor, the mineral container and the terminal, but behind `planner.late`, with the labs, the factory, the power spawn and the nuker (off: nothing used them).
  - **Engine facts (V385 to V402).** A harvest needs an own, active extractor on the mineral's tile and the extractor's `cooldown` at 0 (V385, V386). It yields `HARVEST_MINERAL_POWER` (1) a WORK part (V387) and sets the cooldown to `EXTRACTOR_COOLDOWN` (5), which the engine counts down from the next tick, so one mineral gives a harvest every 6 ticks (V388, V389, inferred from the engine's order). What a creep's store cannot hold goes into a container on its tile first (V387, V193). An emptied mineral refills to `MINERAL_DENSITY` for its density `MINERAL_REGEN_TIME` (50000) ticks later (V390, V391). A container, storage or terminal is one pool for every resource (V401), and a creep can hold energy and a mineral together (V402).
- Options asked (2026-11-25, with the facts above):
  - The sink: (a) the terminal, with the terminal, the extractor and the mineral container split from `planner.late` into a gate of their own; (b) the storage (`planner.storage` on; 30000 energy, RCL4, `STORAGE_CAPACITY` 1000000); (c) both, the storage first.
  - When a room mines: (d) while the sink holds less than a stock cap (`minerals.stock_max`), below every economy and defense role; (e) only once labs or the market ask for the mineral (P9.2, P9.5).
  - Who carries: (f) a dedicated mineral hauler; (g) the energy haulers, which would take a mineral load when the container fills.
- Decision: (a), (d) and (f), the user's choices ("Terminal", "Under a stock cap", "Mineral hauler").
- What it does (`rustedscreep_core::economy::minerals`, glue in `rustedscreep-wasm` `minerals.rs` and `snapshot.rs` `push_mineral`):
  - **The gate.** `planner.minerals` (on) places the terminal (100000 energy), the extractor (5000), the mineral container (5000) and the roads that serve only them, from RCL6 (`planner::layout::Gate::Minerals`). `planner.late` keeps the labs, the factory, the power spawn and the nuker (off).
  - **When a room mines** (`minerals::why`): `minerals.enabled`, a level that allows the extractor and the terminal, an own extractor on the mineral, a container next to it, an own terminal, a mineral type the build knows, a mineral amount above 0, the terminal holding less than `minerals.stock_max` (100000) of the mineral and at least `minerals.free_min` (2000, `CONTAINER_CAPACITY`) free, and a plan.
  - **The plan.** It is built again when its key changes (movement's grid version, the room's capacity, the spawn, container and terminal tiles, `minerals.max_work`, `hauling.margin_pct`), with two flow fields: the miner's walk from the spawn and the haulers' trip from the container to the terminal.
  - **The miner** (`Role::MineralMiner`, name code `e`, priority 65). It has only WORK and MOVE parts. Its body is the one of 1 to `minerals.max_work` (24) WORK parts, with the MOVE parts `sizing::miner_body_work` solves, that harvests the most over its life (`minerals::miner_body`). It stands on the container and calls `harvest` when the extractor's cooldown reads 0 and the container can take a whole harvest, so nothing piles on the ground. One a room, with no pre-spawn replacement.
  - **The haulers** (`Role::MineralHauler`, code `t`, priority 66). They have CARRY and MOVE parts, sized by the source haulers' solver at the miner's rate (`minerals::rate_capacity`). They are requested only once the miner lives (spawning counts), or for a container holding a full load. An empty hauler withdraws the mineral when the container holds a full load for it, or anything while the miner is not harvesting. A loaded one transfers it all to the terminal.
  - **The reads.** The snapshot reads a room's mineral (`mineralAmount`, `ticksToRegeneration`, `mineralType`), the container next to it (its stock of the mineral and everything it holds), the extractor's `cooldown` and the terminal's stock and free room: about 14 JS calls. It reads them every tick the Standard tier runs while a mineral creep of the room out of the spawn can act (the room mines, its container holds some of the mineral, or a hauler carries some), else every `minerals.read_ticks` (100) ticks or when the regeneration is due.
  - **The tiers.** The plans and requests run in a Critical job (`minerals`) before the opening's, requesting only on ticks the Standard tier runs. The creeps' work runs in Standard (`minerals work`).
  - **The upgraders' budget.** While a room mines, its mineral creeps' bodies count in the upgraders' upkeep (`Upgrading::set_minerals`), so the upgraders are sized to what is left.
  - **The console and log.** `rustedscreep.minerals()` shows the rooms; `rustedscreep minerals: <room> mines its <type> (<amount> left)` and `... stopped mining: <why>` log a room's start and stop.
- Added in the implementation, not asked:
  - The haulers wait for the miner. The sandbox showed a hauler, at the higher priority, ordered first and waiting at an empty container while the miner waited for the spawn.
  - The overflow rule follows V183 and V193 (a container on the miner's tile takes the overflow), not the verifier's first reading of V387, which said the overflow reaches the ground.
  - From the hot-path review (2026-11-26, no high finding), applied:
    - The reads follow creeps that can act, not any creep: a spawning miner, or an idle one after a stop with nothing to carry, no longer holds a room to a read every tick.
    - No room is read every tick on a tick without the Standard tier, since no creep acts then.
    - A room dropped from the module (its extractor gone) sets its upkeep to 0, which before stayed in the upgraders' budget.
    - The upkeep list is cleared each tick at `begin`, not at unit 0, which a resumed job may never reach.
    - The plan's flow fields are built only for a room that passes the checks before the plan (`minerals::gate`) or whose container holds the mineral.
    - The miner's WORK count is read from the plan at the harvest, not copied before the plan's build, so the first tick after a reset cannot harvest past the container.
  - Carried from the review, not applied:
    - (medium) A mining room is read every tick (about 14 calls), though the miner can harvest only once every 6 ticks; reads could be predicted from the cooldown and the creeps' distances. Measure with the `profiler` build first.
    - (low) The container's `store` getter is read twice on a read tick.
    - (low) `mineralType` is read and copied on every read, though it never changes.
    - (low) A mineral hauler's energy is read only to be subtracted.
    - (low) There is no hysteresis at `minerals.stock_max`: once P9.2 to P9.5 drain the terminal, each crossing flips the upkeep and rebuilds the upgraders' plan. A band is a tuning choice for the user.
- Consequences:

  - Minerals pile up in the terminal up to the cap until P9.2 to P9.5 use them. The energy spent is about 0.5 energy a mineral unit (`MineralsConfig::max_work`'s TUNING row), and only while the cap is not reached.
  - Nothing is persisted. A reset rebuilds the rooms on their next reads, every room being due on its first tick.
- Risks:
  - The 6-tick harvest period is inferred from the engine's order (V389), not measured. With a 5-tick period the miner would only skip a tick it could have harvested, never call on cooldown, since it reads the cooldown each tick.
  - E7N57 cannot test it live before RCL6. The native tests and the sandbox sim carry it until then.
  - `minerals.stock_max` and `minerals.max_work` are starting values. P9.2 and P9.5 revisit the cap.
- Evidence: V385 to V402; `economy/minerals_tests.rs` (16 tests); `planner/build.rs` and `tests/planner_build.rs` (the gate); `js/tools/mineral-sim.mjs` (check row 27).

    - (medium) Each read scans the terminal's whole store (`Object.keys`, then a string and an amount a key: about 2 + 2K + L calls for K keys, L of them lab resources), though a running job needs only its two reagents and an emptying one only the free room. A read mode per room would cut it.
    - (medium) The room is read on every tick the hauler only walks; its move needs only the targets' tiles from the last read and its own place, which the snapshot always has. Moving on cached tiles and reading only one step from the target would cut most of a job's reads.
    - (low) `has_work` runs up to twice a room a tick; `begin` scans every own structure for terminals and labs; `lab_resource` is a linear search over 41; the Critical `labs` job samples the CPU clock every tick even when no room is read.
- Consequences:
  - At RCL6 a room spends nothing on labs until a second mineral arrives; then 150000 energy for 3 labs, and 50000 more for each lab at RCL7 and RCL8.
  - The compounds pile up in the terminal up to their goals until P10 (and later defense) boosts creeps with them.
  - Nothing is persisted. A reset rebuilds the rooms on their first reads and finishes a loaded job.
- Risks:
  - No reaction can run live until P9.4 or P9.5 brings a second mineral; the native tests and the sandbox sim carry it until then.
  - The reaction period rests on V406's inferred step (the processor's `gameTime` is the tick of the call). The bot reads each output's cooldown before it reacts, so a longer period would cost one refused call, held for `labs.read_ticks`.
  - The goals and `labs.batch_min` are starting values; P10's boost planning revisits them.
- Evidence: V403 to V419; `economy/labs_tests.rs` (21 tests); `planner/build.rs` and `tests/planner_build.rs` (the labs' gate); `js/tools/lab-sim.mjs` (check row 28).

## ADR-046 The factory: what it makes, where its energy comes from, who carries, and when it is built: Accepted (2026-11-26; implemented 2026-11-26)
- Context: ROADMAP P9.3 and SPEC §3.8 ask for the factory. `CONTROLLER_STRUCTURES` allows one factory from RCL7, at `CONSTRUCTION_COST` 100000 (V234, V235).
  - **Engine facts (V420 to V429).** `produce(resourceType)` takes a recipe's components from the factory's store, adds its amount and sets a cooldown deadline (V420, V422, V423). A factory whose level no power creep has set makes only the recipes with no level (V421): the 8 mineral bars (500 of a mineral and 200 energy make 100 bars, cooldown 20), their decompression, the battery (600 energy make 50) and its reverse (50 make 500, a sixth lost), and wire, cell, alloy and condensate from deposit resources the bot never harvests. Every other commodity needs a level, which needs a power creep (P9.7). The store is one pool of `FACTORY_CAPACITY` (50000), and creeps move anything in and out of it with no factory rule (V425, V426).
  - **The energy.** Every recipe needs energy. The storage is off (the user's choice, 2026-11-18), and a room's energy goes to its spawns, extensions, towers and controller container, where the upgraders are sized to spend all of it (P3.4).
  - **The live home.** E7N57 is at RCL5, so no factory can stand there before RCL7.
- Options asked (2026-11-26, with the facts above):
  - What the factory makes: (a) bars from the surplus: each mineral the room holds above a reserve (`factory.mineral_keep`), with batteries and decompression left until terminal balancing (P9.4) or the market (P9.5) asks; (b) a stock-goal list like the labs' (the bars and the battery), with decompression when a mineral runs short; (c) defer the factory to P9.5 or P9.7 with an ADR and no code.
  - The energy: (d) the source haulers fill the terminal after the spawns, extensions and towers, up to `factory.energy_keep`, with the factory's energy counted in the upgraders' upkeep; (e) the factory's carrier takes it from the controller container; (f) turn on the storage as the room's energy bank.
  - Who carries: (g) a factory hauler of its own; (h) the lab hauler serves both; (i) the mineral haulers.
  - When it is built: (j) once it has work: `planner.factory`, split from `planner.late`, places it only where the terminal holds a batch above the reserve; (k) at RCL7, its own switch on; (l) its own switch, off.
- Decision: (a), (d), (g) and (j), the user's choices ("Bars from surplus", "Haulers fill terminal", "Factory hauler", "Once it has work").
- What it does (`rustedscreep_core::economy::factory`, glue in `rustedscreep-wasm` `factory.rs` and `snapshot.rs` `read_factory` and `read_terminal_stock`; `economy::Hauling::set_banks`; `economy::Upgrading::set_factory`):
  - **The recipes** (`factory::recipes`): the 8 minerals with a bar (the 7 base minerals and ghodium, `snapshot::FACTORY_RESOURCES`), each bar's `COMMODITIES` entry kept when it has no level and takes only its mineral and energy, read from the crate once a global (it builds a map a call, V428).
  - **The job** (`factory::pick`): the first of those minerals (the current one first) that the room holds at least a batch above `factory.mineral_keep` (9000) of, counting the terminal, the factory and the hauler's load, while another batch keeps the room's bars of it within `factory.bar_max` (20000). It ends at the reserve or at the cap, with a log line.
  - **The pace** (`factory::pace`). A batch at most every `CREEP_LIFE_TIME / (factory.energy_per_life / a batch's energy)` ticks, rounded up and never sooner than the cooldown: at the default 3000, 15 batches a life, one every 100 ticks, 2 energy a tick. While the room compresses with energy to be had (its sources are hauled, or a batch's energy is at hand), the most it can spend in a life (`factory::life_energy`) and the hauler's body are left out of the upgraders' budget.
  - **The energy** (`Factories::banks`). While a room whose sources are hauled compresses and its terminal holds less than `factory.energy_keep` (1000), the terminal joins the source haulers' fills once the spawns, extensions and towers are full (`Hauling::set_banks`), as the towers joined them in P7.2. A room whose terminal is open, and that is not read in full, has its terminal's energy alone read on the next tick (`store.energy`: 2 calls), so the haulers stop once it is full.
  - **The factory hauler** (`Role::FactoryHauler`, name code `f`, priority 63, below the lab hauler). The lab hauler's body (CARRY and MOVE parts, a MOVE for every 2 CARRY, up to `factory.hauler_carry`, 10). One a room, requested while the factory has work and the Standard tier runs. An empty one takes out of the factory anything but the job's mineral and bar, and the bar once a whole load of it is there; else it loads the job's mineral up to a batch, then energy for a batch, from the terminal. It withdraws from the terminal with the amount and from the factory with none, and transfers with none: the job's mineral and energy to the factory, anything else to the terminal.
  - **Building the factory** (`Factories::wants_factory`). `planner.factory` (on; `planner::layout::Gate::Factory`, split from `planner.late`, which keeps the power spawn and the nuker) places the factory and the roads only it needs, but only in a room that wants one: where an own factory stands, or where `pick` finds a job in what the room holds (`Placement::set_factory_rooms`, `Gates::with_factory`).
  - **The reads.** A room is tracked with an own factory, an own terminal at a level that allows a factory, or a factory hauler. Its terminal's stock (one pass over the store's keys, shared with the labs' read) and its factory's (`store`, free room, keys and amounts, `cooldown`) are read every tick the Standard tier runs while the hauler is out with work, on the tick after a batch, on the tick the next batch is due, and otherwise every `factory.read_ticks` (100).
  - **The tiers.** `factory` (Critical, before the hauling job and the spawn plan: the job, the bank, the upkeep, whether the room wants a factory, the request) and `factory work` (Standard: the batch's order and the hauler's intents). The act step calls `produce` after the labs' reactions, bound with `catch`; a refused call holds the room's batches for `factory.read_ticks` and logs once.
  - **The console and log.** `rustedscreep.factory()`; `rustedscreep factory: <room> compresses its <mineral> into <bar> (<n> held, <keep> kept)` and `... stopped compressing its <mineral> (<n> batches): at its reserve | at the bar cap | off`.
- Added in the implementation, not asked:
  - The bar cap (`factory.bar_max`), so bars cannot fill the terminal while nothing sells them; and the pace (`factory.energy_per_life`), which makes the upkeep the upgraders leave out a fixed amount a life and stops a backlog of surplus from taking half a room's energy at the cooldown's rate (75 batches a life, 15000 energy).
  - From the sandbox sim's first run: a room with no hauled source opened its terminal and read its energy every tick for nothing; the bank now opens only where a source is hauled.
  - The bank read, and the energy counted in the upkeep only while it can come (hauled sources or energy at hand), so a room whose sources are all linked does not shrink its upgraders for a factory that cannot run.
  - From the native tests: a batch did not ask for a read, so the hauler, which had worked from the read before it, idled a whole pace before reloading. The tick after a batch is now read (`a_due_batch_asks_for_no_read_without_the_standard_tier`).
  - A terminal is tracked only at a level that allows a factory, so an RCL6 room pays no factory reads.
  - From the hot-path review (2026-11-26; no high finding), applied:
    - (medium) The hauler's body counted in the upkeep only while it had a task, which flipped twice a batch and rebuilt the upgraders' plan (a whole-room flow field) each time; it now counts for the whole job.
    - (medium) Work was judged as if the hauler were empty even when it held a load with nowhere to go (a full terminal), so the room was read in full every tick for nothing; work is now judged per hauler (`a_load_with_nowhere_to_go_keeps_no_read_going`), as ADR-045 fixed for labs.
    - (low) The bank read also read the terminal's free room and threw it away; it is now 2 calls. The read lists come from one call, with no per-tick copy. The recipe table is built once a global, from the first tracked room, whatever it holds. A factory in a room below its level gets no job, and a budget that pays for no batch starts none (`no_job_below_the_factorys_level_or_without_a_batch_paid_for`). A bank opens only while its terminal stands this tick. The snapshot's doc comments give the true call counts (2 a key, 1 more a key used).
  - Carried from the review, not applied (measure with the `profiler` build first):
    - (medium) The factory hauler's store is read every tick (4 calls), though only the module's read ticks use it. Reading it only then needs a "store known" mark in the snapshot, since a loaded hauler read as empty off a read tick would ask for a read every other tick. The lab hauler has the same pattern.
    - (low) An open bank is read every tick, even on ticks no source hauler can deliver (the spawns or towers have room); hauling could say which rooms it sent a hauler to the terminal.
    - (low) As ADR-045's carried items: the Critical job samples the clock every tick with a tracked room, `begin` scans every own structure and creep, each read scans the whole stores (a `String` a key), the room is read on every tick the hauler only walks, and `factory_resource` is a linear search over 16.
- Consequences:
  - At RCL7 a room with a surplus mineral builds a 100000-energy factory, then spends up to `factory.energy_per_life` a creep life on bars, which pile up in the terminal to `factory.bar_max` until P9.5 sells them or P9.7's power creeps raise the factory's level.
  - The source haulers stop at the terminal before the controller container while it is open, so the upgraders get that energy later or not at all; their budget already leaves it out.
  - Nothing is persisted. A reset picks the job again from the next read, and the pace starts over (one batch may come early).
- Risks:
  - E7N57 cannot run it live before RCL7. The native tests and the sandbox sim carry it until then.
  - With all sources linked (`links.source_links` 2), no hauler passes the terminal and the factory makes nothing; its energy is then not counted against the upgraders.
  - The cooldown's tick offset is inferred (V423). The module reads the cooldown before each batch and paces at least the cooldown, so a longer period would cost one refused call, held for `factory.read_ticks`.
  - `factory.mineral_keep`, `factory.bar_max`, `factory.energy_keep` and `factory.energy_per_life` are starting values; P9.4 and P9.5 revisit them.
- Evidence: V420 to V429; `economy/factory_tests.rs` (16 tests); `economy/tests.rs` (`a_banked_terminal_is_filled_after_the_spawns_up_to_its_mark`); `planner/build.rs` and `tests/planner_build.rs` (the factory's gate); `js/tools/factory-sim.mjs` (check row 29).

## ADR-047 Terminal balancing: what moves between the rooms' terminals, and where a send's fee comes from: Accepted (2026-11-26; implemented 2026-11-26)
- Context: ROADMAP P9.4 and SPEC §3.8 ask for terminal balancing. A terminal (one a room from RCL6, V393) holds up to `TERMINAL_CAPACITY` (300000) of any resource in one pool and can send a resource to a terminal in another room.
  - **Engine facts (V430 to V446, the send path read byte-exact at a90d26f).** `send(resourceType, amount, destination)` checks the owner, the room's level, the destination's name, the type, the stock, the cooldown and then the fee, in that order (V435). The fee is `ceil(amount × (1 − e^(−range / 30)))` energy from the sender (V432), where the range is the larger of the two rooms' horizontal and vertical distance, wrapped around the world's edge (V433). The send happens in a global pass after the rooms' intents (V437): it is dropped, with no cooldown, on a cooldown or to a room with no terminal or one with no owner; the amount is clipped to the destination's free room, and the fee is paid only for what arrives (V438). The engine never compares the two owners, so a send to another player's terminal is delivered (V438). A terminal sends at most once a tick (V436), and a send sets a cooldown of `TERMINAL_COOLDOWN` (10) ticks (V437, V441). `TERMINAL_SEND_COST` (0.1) and `TERMINAL_MIN_SEND` (100) are not rules: no file of the send path uses them (V431). screeps-game-api's `send` has no `catch` and unwraps an unknown return code (V444).
  - **Why it matters.** A room's labs react only from its own terminal (ADR-045), and a room mines only its own mineral (ADR-044). So with no imports, no room ever holds both reagents of a first reaction, and the labs never run.
  - **The energy.** The storage is off (the user's choice, 2026-11-18), so a terminal holds energy only from the factory's bank (ADR-046), which opens only while the factory compresses.
  - **The live home.** E7N57 is the only owned room, at RCL5, with no route out (ADR-043), so nothing can run live until two rooms have terminals.
- Options asked (2026-11-26, with the facts above):
  - What moves: (a) the base minerals: each terminal filled up to `terminals.mineral_keep` of each of the 7, from the terminals that hold more than the keep plus a margin, with compounds and bars left where they were made until P10's boosting or P9.5's market moves them; (b) the base minerals and the labs' seven target compounds, each to its own keep, so every room has boosts on hand for P10; (c) one hub room that every room sends its minerals above a small keep to, which runs all the reactions and compression.
  - The fee: (d) while a send waits for its fee, the source haulers fill the terminal up to `terminals.energy_keep` after the spawns, extensions and towers (the bank ADR-046 opened for the factory); (e) a send waits until the terminal holds its fee from the factory's bank, with no new fill; (f) also move energy from terminals above a mark to those below it.
- Decision: (a) and (d), the user's choices ("Base minerals", "Haulers fill the fee").
- What it does (`rustedscreep_core::economy::terminals`, glue in `rustedscreep-wasm` `terminals.rs` and `snapshot.rs` `read_balance`; `economy::Hauling::set_banks`):
  - **The members.** Each owned room with an own terminal at a level that allows one (`CONTROLLER_STRUCTURES`): a terminal below its level takes nothing (V439), so it neither gives nor receives. Only the members' own terminals, read this tick, are destinations, since the engine would deliver to anyone's terminal (V438). With fewer than two members nothing is read, so a lone RCL6 room pays nothing.
  - **The fee and the range** (`terminals::fee`, `terminals::range`): V432's formula in Rust, over the larger coordinate difference of the two rooms (`RoomName::x_coord`, `y_coord`, V446) with no wrap, which can only make it longer, so the fee is never below the engine's. No JS call (`Game.market.calcTransactionCost` would cross into JS, V445).
  - **The plan** (`terminals::plan`). A member holding less than `terminals.mineral_keep` (3000, `LAB_MINERAL_CAPACITY`) of a base mineral, by at least `terminals.send_min` (1000), needs the difference; a member gives only what it holds above the keep. The needs go largest first, then by mineral, then by room. Each is served by the nearest giver with at least `send_min` to give (the lowest fee), then the one with the most, then by room. A send moves the least of the need, the giver's surplus, the receiver's free room (less what this plan already sends it) and the most `terminals.energy_keep` pays the fee of; never under `send_min`. A terminal sends once a plan, and a receiver gets each mineral from one giver a plan. A receiver ends at most at the keep and a giver at least at it, so nothing flows back. Pairs beyond `terminals.max_range` (10 rooms) do not trade. The plan is the same for the same reads in any order.
  - **The fee's energy (the user's choice).** A giver on its cooldown waits for it. One off its cooldown that lacks the fee sends what its energy pays for when that is at least `send_min`. Otherwise, where its sources are hauled, the send waits: the terminal joins the source haulers' fills after the spawns, extensions and towers up to `terminals.energy_keep` (1000), through `Hauling::set_banks` with the factory's banks, and its energy alone is read each tick the Standard tier runs (2 calls). A giver that lacks the fee where no hauler can bring it is passed over for the next giver.
  - **The reads.** On a plan tick every member is read in full (`store`, free room, energy, the 7 base minerals and `cooldown`: 11 calls, or 2 more than the labs' read when they read its stock that tick). A plan is due `terminals.read_ticks` (100) after the last, `TERMINAL_COOLDOWN` after one that ordered a send, when a giver waiting on its cooldown comes off it, and on the tick after a waiting giver's energy read shows its fee. Reads are asked for only after a tick the Standard tier ran.
  - **The tier.** `terminals` (Standard, one unit: the plan on a tick every member was read, or the waiting fees on another). The banks are set after the factory's Critical job and before the hauling job. The act step calls `send(resourceType, amount, destination)` after the factory's batches, through a binding of its own with `catch`; no description is passed. A refused call holds that giver for `terminals.read_ticks` and logs once.
  - **The console and log.** `rustedscreep.terminals()`; `rustedscreep terminals: <from> sends <amount> <type> to <to> (fee <fee>, range <range>)` on each accepted send, and `... <from>'s send of <amount> <type> to <to> was refused at tick <t>: <error>; it waits <n> ticks`.
- Added in the implementation, not asked:
  - `terminals.send_min` (each send is an intent and a cooldown, and the fee is the same share of any amount, so a floor trades only CPU), `terminals.max_range`, and the cap of a send to what `terminals.energy_keep` pays the fee of, so a waiting send can always be paid.
  - The plan runs only on a tick every member was read, so it never works from a stock an earlier send has changed.
  - A giver that lacks the fee and cannot be filled is passed over, so a need is not left waiting on a room whose sources are all linked or not mined.
  - `Hauling::set_banks` keeps the larger want of a room named twice (the factory's bank and a send's fee), where it kept an arbitrary one (`a_room_banked_twice_keeps_the_larger_want`).
  - From the native tests: on the tick a waiting send went out, its terminal stayed open to the haulers and was read for its energy on the next tick for nothing; the bank now closes with the plan.
  - The balance read takes the base minerals from the labs' stock pass when the labs read the terminal that tick.
  - From the hot-path review (2026-11-26; one high), applied:
    - (high) A send waiting for its fee kept its terminal open to the haulers for good once the room was left with no other member (a terminal destroyed, a room below RCL6 or lost): no plan ran to end the wait and no read refreshed the want, so the haulers kept carrying energy there after the spawns, extensions and towers. With fewer than two members, or off, nothing waits and no bank opens now (`a_lost_member_closes_the_bank`, which fails without the fix).
    - (medium) The bank opens only while the Standard tier runs, as the factory's does, since only then is the waiting terminal's energy read (`no_bank_without_the_standard_tier`).
    - (medium) A ready send whose giver's terminal a creep withdraws from on the same tick (a lab or factory hauler taking a mineral or the factory's energy) waits for the next tick (`Wait::Busy`, through `IntentBuffer::withdraws_from`; `a_creeps_withdrawal_delays_the_send`): the room pass makes the two in an order the bot does not know and drops a send left short with no refusal (V436).
    - (medium) Each ordered send commits its intent's CPU (`INTENT_CPU_COST`, V34) to the tick's budget, as the labs' reactions and the factory's batches do.
    - (low) The next tick's reads are asked for only when the `terminals` job ran, not only when the tier allowed it, so a job the budget cuts does not read every terminal each tick it is cut. The bank's want stays within the terminal's free room, a full giver short of its fee is passed over, and the bank names the terminal standing this tick, not the last read's. Every fee leaves `terminals::FEE_MARGIN` (1) energy unspent, for the last-digit difference between Rust's and JavaScript's `exp`. `begin` checks a structure's type before its room.
  - Carried from the review, not applied (measure with the `profiler` build first):
    - (low) A waiting giver's energy is read every Standard tick even when no hauler reached its terminal (2 calls a waiting member a tick, for up to `terminals.read_ticks`); hauling could say when a hauler filled a bank.
    - (low) The balance read reuses the labs' stock pass but not the factory's, whose first 7 resources are the same base minerals, and reads the cooldown and energy of members that only receive.
    - (low) The counters count an accepted send that the engine then dropped or clipped (a receiver filled by a creep the same tick); the next plan's read shows the truth.
- Consequences:
  - At RCL6 in two or more rooms, each room's terminal holds up to 3000 of every base mineral another room mines, so each room's labs can start any first reaction (ADR-045's `pick`), and `planner.labs` builds the labs there once one is on hand.
  - A giver pays at most `ceil(3000 × (1 − e^(−10 / 30)))` = 851 energy a send. That energy comes from the haulers' deliveries after the spawns, extensions and towers, and is not left out of the upgraders' budget (the factory's energy is, ADR-046): at most `terminals.energy_keep` a wait.
  - Nothing is persisted. After a reset the members are read on the next Standard tick and planned from scratch.
- Risks:
  - Nothing can run live until two owned rooms have terminals. The native tests and the sandbox sim carry it until then.
  - A creep's withdrawal from the giver's terminal on the send's tick holds the send a tick (`Wait::Busy`), but only for the intents the jobs before `terminals` queued; a creep intent queued after it (none today) could still leave the send short, which the engine drops after the game side answered OK.
  - The fee is computed with Rust's `f64::exp`, the engine's with JavaScript's `Math.exp`. `terminals::FEE_MARGIN` keeps one energy spare for a last-digit difference at an exact boundary; past it, the call would be refused (ERR_NOT_ENOUGH_RESOURCES), logged, and held for `terminals.read_ticks`.
  - The cooldown's tick offset is inferred (V441). The module reads the cooldown before each plan and waits for it, so a longer period costs one plan a tick later.
  - `terminals.mineral_keep`, `send_min`, `energy_keep` and `max_range` are starting values; P9.5's market revisits them.
- Evidence: V430 to V446; `economy/terminals_tests.rs` (22 tests); `js/tools/terminal-sim.mjs` (check row 30); the hot-path review (2026-11-26).
