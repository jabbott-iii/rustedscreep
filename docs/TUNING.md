# Tuning guide (SPEC §6.5)

This guide mirrors `crates/rustedscreep-core/src/config.rs` field for field, and a doc-sync test fails when the two diverge.
Each row gives the default (the value of the `mmo` profile, which serves the MMO, the official persistent massively multiplayer server), the unit, the rationale (with a measurement or source), the safe range,
the runtime key, and the other server profiles whose value differs.

- **Safe range.** The cell starts with the code's range (`config::FIELDS`), which runtime overrides are clamped to. A constraint
  between two fields (`config::RULES`) is stated after it and names the other field; an override that breaks one is refused.
- **Runtime key.** The key for `rustedscreep.configSet(key, value)` (P1.10, the config module), or `none` where only a profile sets the value: the
  loader's values (the loader is the JavaScript that boots the bot's WebAssembly (wasm) module) are built into the bundle, the profiler's values and the segment ids (the numbers of the RawMemory segments, the stored strings the bot keeps data in) are fixed for a global (one lifetime of the bot's JavaScript environment on the server; a global reset replaces it with a fresh one and loses everything in its heap), and a phase gate's target (`MiningConfig::harvest_efficiency_pct`, the level a roadmap phase's exit check compares its measured harvest efficiency with) is read by no tick (a tick is one game turn).
  The bot's work runs in three tiers: Critical work (spawning, defense, and harvesting) runs at any bucket, up to the tick's CPU ceiling
  (`SchedulerConfig::tick_reserve_pct`) and until the tick's clock breaks (`SchedulerConfig::bad_samples_to_break`; ADR-013, the
  decision on when Critical work stops); Standard work (hauling, upgrading, building, and offense operations) runs unless the bucket
  (the player's store of CPU that ticks leave unused) is critically low; and Optional work (planning, the market, scouting, visuals,
  pixels, and offense planning) runs only above bucket thresholds. Overrides take
  effect on the next tick, are kept in `PersistConfig::config_segment` across global resets, and load a tick or two after a global
  starts (with the Standard tier; until then, and while the bucket is below the Standard gate, the profile's values apply).
  `rustedscreep.config()` lists every key with the value in force, `configUnset(key)` and `configReset()` remove overrides.
- **Profile overrides.** Each other profile in `config::PROFILES` whose value differs, as `name: value`; `none` while `mmo` is the
  only profile (the optional roadmap tracks, for a private server and for the Seasonal server, add `private` in PS1 (private
  server setup) and `season` in SE2 (the season profile and its modules)).

| `SchedulerConfig::tick_reserve_pct` | 10 | percent | The engine (the server's game code) kills a tick with a wall-clock timeout at tickLimit + 5 ms (at least 30 ms; V105), but the scheduler's clock is isolate CPU time (the CPU time of the V8 isolate, the sandboxed JavaScript engine instance that runs the bot) plus intent CPU (V106; an intent is a game action the bot orders for the tick, such as a move or a harvest), and nothing reconciles the two. Running past tickLimit costs either way: a killed tick is an aborted tick, which the loader recovers from with a global reset (ADR-003), and while the bucket is below 500 − limit, tickLimit is bucket + limit (V37), so a tick that runs past it without being killed is billed into a negative bucket and the next tick is skipped. So no tier plans to use all of tickLimit. 10% (50 CPU at tickLimit 500, 2 at an empty bucket with limit 20) covers the work after the decide step (flushes, the loader; each tick runs a snapshot, which copies the game state into Rust, then the decide step, which chooses the intents, then the act step, which issues them), the overshoot of the units (the small pieces of work, such as one room, that a time-sliced job runs between clock readings) since the last clock sample (a batch's expected cost is at most a quarter of this reserve, so a cost that jumps up to 4 times overshoots by at most half of it, plus one unit), and drift between CPU and wall time. Intents for the act layer are committed separately (0.2 CPU each, V34), but the act step's JavaScript (JS) calls themselves (one per issued intent, free say and pull included, plus a string decode per say; P1.7, the act layer) run after the decide step and only this reserve covers them. If a tick's committed CPU were all intents (N ≤ ceiling / 0.2, the ceiling being tickLimit less this reserve), the reserve would hold N calls only if one call costs at most 0.1 × 0.2 / 0.9 ≈ 0.022 CPU (`rustedscreep_core::profiler::act_call_bound`, 22222 µCPU, millionths of a CPU). That is a necessary condition only: it gives the whole reserve to billed calls and counts no free ones, so the safe cost per call is lower. A `profiler` build measured the act step on the MMO (`act per call` in `rustedscreep.profiler()`, `act.net / act.calls` against `callBound` in the stats segment, the RawMemory segment the profiler writes, both net of the profiler's own reading; module 8 of P1, the profiler): 0.0076 CPU a call over 861 ticks with calls, against the 0.0222 bound (V209). Starting value; the profiler's `act` series measures the act step (minus `clock` for its own cost), and the fault log after it has no series of its own. | 5 to 50 (the config test checks it) | `scheduler.tick_reserve_pct` | none |
