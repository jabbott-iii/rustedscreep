# Tuning guide (SPEC §6.5)

This guide mirrors `crates/rustedscreep-core/src/config.rs` field for field, and a doc-sync test fails when the two diverge.
Each row gives the default, the unit, the rationale (with a measurement or source), the safe range (overrides are clamped to it),
and the server profile, if the value differs by profile.

| Field | Default | Unit | Rationale / evidence | Safe range | Profile overrides |
|---|---|---|---|---|---|
| `LoaderConfig::boot_bucket_min` | 1500 | CPU | The starter's gate (VERIFICATION_LOG V17), kept until the P1 cold-start measurement on the MMO sets it. In the sandbox a boot costs about 3 ms of CPU-like time (V99), far below it; the MMO number decides. | 0 to 10000 (`CPU_BUCKET_MAX`; the config test checks it) | none |
| `LoaderConfig::boot_split_ticks` | true | flag | Compile on one tick and instantiate on the next, so one tick never pays for both as the wasm grows. Costs one tick of boot latency (sandbox: booted in 1 tick, V99). | true or false | none |
| `LoaderConfig::recovery_mode` | halt | enum | ADR-003: `Game.cpu.halt()` (a) is the proven default. Re-instantiation (b) recovered 10 of 10 traps in the sandbox in 2 ticks against 3 for halt (V99), but stays off until the MMO trap-test measures it. Without `Game.cpu.halt`, halt mode falls back to (b). | halt or reinstantiate | none |
| `LoaderConfig::backoff_window_ticks` | 1000 | ticks | An incident continues the streak if it comes less than this plus the delay then in force after the previous one; otherwise a new streak starts. Long enough to see a crash loop, short enough to forget a one-off trap. Starting value; revisit after live incidents. | 100 to 20000 | none |
| `LoaderConfig::backoff_incidents` | 3 | count | One trap or aborted tick recovers at once; the third consecutive incident marks a loop, so the next boot waits. Also caps re-instantiations per window in mode (b). Trap-test traps do not count. | 1 to 20 (the loader keeps the last 20 incidents) | none |
| `LoaderConfig::backoff_base_ticks` | 100 | ticks | First delay once backoff starts, doubling per further consecutive incident (a persistent trap in the sandbox waits 100, 200, 400, ... 3200 ticks; V99). An idle bot refills about 20 CPU per tick at the free-tier limit (V37), so 100 ticks restore about 2000 CPU, above the boot gate. | 1 to `backoff_max_ticks` (the config test checks it) | none |
| `LoaderConfig::backoff_max_ticks` | 3200 | ticks | 100 × 2^5: caps the wait so the bot always retries without human action. | `backoff_base_ticks` to 20000 | none |
| `LoaderConfig::notify_group_minutes` | 60 | minutes | `groupInterval` for `Game.notify`, which batches messages into that window (V96); hourly keeps a crash loop from flooding email. | 0 to 1440 (the driver clamps to it, V96) | none |
| `LoaderConfig::trap_test_max` | 20 | count | Most traps one `rustedscreep.trapTest(n)` may schedule. The P1 gate needs 10 (the config test checks at least 10); the cap stops a mistyped command. | 10 to 100 | none |
| `SchedulerConfig::tick_reserve_pct` | 10 | percent | The engine kills a tick with a wall-clock timeout at tickLimit + 5 ms (at least 30 ms; V105), but the scheduler's clock is isolate CPU time plus intent CPU (V106), and nothing reconciles the two. Running past tickLimit costs either way: a killed tick is an aborted tick, which the loader recovers from with a global reset (ADR-003), and while the bucket is below 500 − limit, tickLimit is bucket + limit (V37), so a tick that runs past it without being killed is billed into a negative bucket and the next tick is skipped. So no tier plans to use all of tickLimit. 10% (50 CPU at tickLimit 500, 2 at an empty bucket with limit 20) covers the work after the decide step (flushes, the loader), the overshoot of the units since the last clock sample (a batch's expected cost is at most a quarter of this reserve, so a cost that jumps up to 4 times overshoots by at most half of it, plus one unit), and drift between CPU and wall time. Intents for the act layer are committed separately (0.2 CPU each, V34), but the act step's JS calls themselves (one per issued intent, free say and pull included, plus a string decode per say; P1.7) run after the decide step and only this reserve covers them. If a tick's committed CPU were all intents (N ≤ ceiling / 0.2), the reserve would hold N calls only if one call costs at most 0.1 × 0.2 / 0.9 ≈ 0.022 CPU (`rustedscreep_core::profiler::act_call_bound`, 22222 µCPU). That is a necessary condition only: it gives the whole reserve to billed calls and counts no free ones, so the safe cost per call is lower. Unverified until a `profiler` build measures the act step on the MMO (`act per call` in `rustedscreep.profiler()`, `act.net / act.calls` against `callBound` in the stats segment, both net of the profiler's own reading; module 8, live number pending). Starting value; the profiler's `act` series measures the act step (minus `clock` for its own cost), and the fault log after it has no series of its own. | 5 to 50 (the config test checks it) | none |
| `SchedulerConfig::standard_bucket_min` | 2000 | CPU | Below it only Critical work runs (SPEC: Standard stops when the bucket is critically low). It is at least the loader's boot gate (`LoaderConfig::boot_bucket_min`, 1500) plus `CPU_TICK_LIMIT_MAX` (500; the config test checks it): Standard switches on from the bucket at the start of the tick, and one tick is billed about tickLimit at most (the scheduler stops every tier at the ceiling, and the reserve covers the rest) while it refills the limit (V37). So a Standard tick leaves the bucket at or above the boot gate, and a global reset in a CPU deficit can still boot at once (a deferred boot runs no code at all). At the MMO's limit of 20 the refill also covers the up to 1 CPU of ceil billing (V106). Below it the bucket refills by the limit minus Critical use each tick. | `LoaderConfig::boot_bucket_min` + `CPU_TICK_LIMIT_MAX` (2000) to `SchedulerConfig::optional_bucket_min` | none |
| `SchedulerConfig::optional_bucket_min` | 3000 | CPU | Floor for the Optional tier. At the free-tier limit of 20 the surplus formula already turns Optional off below 7000 (`bucket_target` minus limit × `surplus_spread_ticks`), so this floor binds only for limits above 60 (CPU Unlock, V35). | `standard_bucket_min` to `bucket_target` | none |
| `SchedulerConfig::bucket_target` | 9000 | CPU | At this bucket the Optional cap equals the CPU limit, so Optional work that fills its cap uses what the tick would otherwise leave unused (refill = limit − used, V37). Below it the cap shrinks and the bucket refills; above it the surplus is spent. The cap is checked during the decide step, so the work after it, the slicer's overshoot and ceil billing (V106) come on top: with heavy Optional demand the bucket settles slightly below the target (about `surplus_spread_ticks` CPU lower per CPU of that excess per tick), roughly 1000 below `CPU_BUCKET_MAX`, as a reserve for attacks and resets; with light demand it fills up. The pixel policy (P9; a pixel costs the full 10000, V38) will revisit this. Starting value; tune from live bucket data. | `optional_bucket_min` to 10000 (`CPU_BUCKET_MAX`) | none |
| `SchedulerConfig::surplus_spread_ticks` | 100 | ticks | The Optional cap moves 1 CPU per this many CPU of bucket away from the target: limit + 10 at a full bucket (30 at the free tier), 0 at 7000. A surplus spent at the cap shrinks by a factor of 1 − 1/100 per tick, so it is spent over about 100 ticks, not in one burst. | 10 to 10000 (0 would divide by zero; the code reads it as 1) | none |
| `SchedulerConfig::optional_warmup_loops` | 1 | loops | The first tick of a new global (after a global reset or a re-instantiation) runs no Optional work (wasm-bot rule): that tick already paid for instantiation and the first full snapshot. Starting value; the cold-start measurement in the P1 gate may raise it. | 1 to 100 (the config test checks at least 1) | none |
| `SchedulerConfig::max_units_per_sample` | 16 | units | A time-sliced job reads the clock after at most this many units. The first batch of every call is one unit, so a cost that changed since the last tick is measured first; after that a batch is also limited to half of what is left before the cap and a quarter of the reserve at the measured cost. This count bounds the overshoot when the cost jumps by more than the reserve allows (for example a unit that suddenly needs a path search), and in units too cheap to measure. Each sample is one `Game.cpu.getUsed()` call, whose cost is not known (V106); a `profiler` build measures it (series `clock`, module 8; live number pending), which may move this value. | 1 to 256 | none |
| `SchedulerConfig::bad_samples_to_break` | 2 | readings | After this many NaN, infinite or negative `getUsed` readings in one tick, the clock counts as broken and every tier, Critical included, stops for the rest of that tick (ADR-013). One bad reading keeps the last good one and work goes on; a second means the scheduler cannot know how close the tick is to the wall-clock kill (V105), and an aborted tick costs a global reset (ADR-003), while stopping costs the rest of one tick's work. Negative readings on the MMO are a user report only (V106, unverified); a reading lower than the last but not negative (a `cancelOrder` refund) is simply raised to the last. | 1 to 8 | none |
| `SchedulerConfig::fault_reports_per_window` | 10 | reports | One budget per window for all jobs and units: at most 10 fault lines per window, then one note when the window closes with the count of the rest and the names of up to 4 jobs whose faults were held back, so a stuck unit can neither flood the console nor hide a new failure elsewhere. Every fault is still counted (`rustedscreep.scheduler()`). | 1 to 100 | none |
| `SchedulerConfig::fault_window_ticks` | 100 | ticks | The window for the fault rate limit. A fault shows up within 100 ticks: as a line if the window still has reports left, otherwise by job name in the window's closing note. A unit failing every tick costs at most 10 lines per 100 ticks. | 10 to 10000 | none |
| `ProfilerConfig::window_loops` | 1000 | loops | Loops per statistics window (a global's first loop is kept apart as the cold loop). The ROADMAP's evidence rule reports CPU as mean and p95 over at least 1000 ticks, so a window is the smallest unit of evidence; a window counts loops; ticks without a loop between its first and last loop are its `gaps` (those before its first loop follow from the previous window's `last`). The open window holds 8 `u32` per loop in the heap (32 KB at 1000), reserved once per global, and a global reset loses it. Closing it costs 8 O(n) selections plus the segment write (measured as `lastFlush`). | 1000 to 10000 (the config test checks it) | none |
| `ProfilerConfig::history_windows` | 8 | windows | Closed windows kept in the heap and written to the stats segment, so a reader that fetches the segment at least once every 8 windows misses none in a global (a global reset starts a new history, and the segment keeps the old one until the next window closes). The worst-case segment text with this many windows must fit `MEMORY_SEGMENT_SIZE_LIMIT` (V41; the profiler's test checks it for 32). | 1 to 32 (the config test checks it) | none |
| `ProfilerConfig::stats_segment` | 99 | segment id | The highest id, away from the persistence segments. The segment manager (module 9) reserves it: it never activates or writes it, and in a `profiler` build it keeps one of the 10 save keys free for it unless the key is already present (V41, V85, V119). The profiler writes it without activating it, once per window, which the driver saves at the end of the tick; it skips the write (one log line) when the key is new and 10 keys are already present, which only segments activated from the console can cause, and the manager then re-issues its active set to drop them. | 0 to 99 (`MEMORY_SEGMENT_COUNT`; the config test checks it) | none |
| `PersistConfig::max_active_segments` | 8 | segments | Most segments the manager keeps active at once. Records live in the heap, so segments are activated only to be read (once per global, or when an owner asks) and dropped from the set afterwards; this caps a burst of loads, for example at boot. Every active segment is a key the end-of-tick save counts (V119), so 8 leaves 2 of the 10 (`MEMORY_SEGMENT_SAVE_LIMIT`): one for the profiler's segment 99 on a window-closing tick and one for a write; writes to keys already present need none, and a write that finds no key waits a tick. Loading into the isolate is not billed (V122), so a wider burst costs only the reads the owners do. | 1 to 9 (`MEMORY_SEGMENT_ACTIVE_LIMIT` and one below `MEMORY_SEGMENT_SAVE_LIMIT`; the config test checks it; the manager also clamps to 1..=10) | none |
| `PersistConfig::load_retries` | 3 | ticks | A segment requested on tick N is loaded on N + 1 (V116), so a missing one means a console `setActiveSegments` replaced the set (console commands run after `loop`, V118) or the server lagged. Each such tick counts a try and re-issues the set; after 3 the load fails and the owner rebuilds from game state, which is always possible. A rebuild costs more than a few ticks of waiting, but an owner should not wait long without its data. Starting value. | 1 to 20 (the config test checks it) | none |
| `PersistConfig::max_writes_per_tick` | 2 | segments | Writes go out after the act step, where only the tick reserve covers them (`SchedulerConfig::tick_reserve_pct`, 50 CPU at tickLimit 500 whenever the Standard tier runs). A full segment (76781 payload bytes) took about 0.95 ms to encode, checksum and hand to JS in the ADR-004 microbenchmark. In the sandbox self-test (`node js/tools/persist-sim.mjs`, which writes a full segment twice) encode plus the JS write took about 9 to 14 ms on the first large crossing of a global, while the polyfill's decoder warms up, and 1.2 to 2.2 ms after. So 2 cap the flush near 4 ms when warm and near 28 ms in the worst case of two cold full writes, inside the 50 CPU reserve the Standard gate guarantees; dirty records beyond that wait a tick. Revisit with `rustedscreep.persistTest()` on the MMO (its first run in a global is the cold case). | 1 to 10 (`MEMORY_SEGMENT_SAVE_LIMIT`; the config test checks it) | none |
| `PersistConfig::self_test_segment` | 98 | segment id | The segment `rustedscreep.persistTest()` writes and reads back: next to the profiler's 99 and away from the low ids later owners take. Its content is a test pattern that nothing else reads. | 0 to 99 (`MEMORY_SEGMENT_COUNT`), not `ProfilerConfig::stats_segment` (the config test checks both) | none |

Groups to cover as they land:
- Bucket tiers (P1). The loader's boot gate, recovery and backoff values are above (P1.4); they live in config.rs's `LOADER_MMO` and are injected into the bundle at build time, so they cannot be overridden at runtime. The scheduler's tier gates, reserve, surplus policy, sampling and fault rate limit are above too (P1.6, `SCHEDULER_MMO`); runtime overrides arrive with module 10.
- Cache TTLs and toggles (P1 onward).
- Spawn lead time (P5).
- Remote profitability cut-offs (P6).
- Defense and safe-mode triggers (P7).
- Expansion limits (P8).
- Market sanity limits and pixel threshold (P9).
- Offense budgets and abort thresholds (P10).
- Breaker cooldown, caps, gates and the "no regrets" threshold (P11).
